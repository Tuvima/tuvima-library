# TVDB setup, TV season matching, and people enrichment

Status: locally implemented, updated September 29, 2026. This document records the product intent, technical plan, and release checks for the editor flow informed by the attached mockups.

## Product walkthrough

1. **Connect movie and TV services during setup.** After adding a Watch library, an administrator sees both TMDB and TVDB in the provider step, including when a credential was previously supplied and restored from configuration or a backup. Both require credentials supplied for this installation; Tuvima ships with no API key and makes no proxy request on the user's behalf. Each card shows a masked configured state and offers Review connection, Replace, and Test. TMDB serves movies only; TVDB serves television shows, seasons, and episodes. The TVDB guide links to its current project/API process and asks for the credential appropriate to the installation's approved access model. It explains any subscriber PIN requirement before the user enters secrets. **Work packages A and B.**
2. **Find a TV match at the level being edited.** In the TV editor, a user can select the show, a season, or an owned episode. Find a match searches that exact level. The season flow shows season artwork, title/number, dates where available, and a preview of its episode range. The episode flow follows the attached mockups' dark bordered list, season selector, filter, stills, selected row, and fixed source-to-target confirmation area. The action states clearly that only the selected season or owned episode will change. Search and selection alone never edit the library; Match applies the change. **Work packages C and D.**
3. **See the right imagery and credit.** TVDB show backgrounds and clear logos, season posters/backgrounds when supplied, and episode stills are downloaded into the existing managed artwork system. Each image is attached to the correct show, season, or episode. Screens displaying TVDB data include visible attribution with a direct TVDB link. Existing custom artwork remains preferred. **Work packages E and F.**
4. **Refresh without applying TMDB to television.** Existing TMDB TV identities remain visible as historical matches so an administrator can review them. New TV searches, matches, ingestion, and provider artwork refreshes use TVDB only. A legacy TMDB TV item needs a deliberate TVDB rematch before TV provider artwork refreshes; if TVDB is unavailable, the operation pauses with a useful message and keeps stored data intact. The app never silently replaces an episode or borrows another episode's still. **Work packages B, C, and E.**
5. **Complete people details for shows such as Solo Leveling.** Cast and eligible crew linked to owned TV content receive a usable person record and detail/portrait enrichment where the source provides evidence. A missing Wikidata QID is not by itself a reason to leave a person empty. Show credits remain distinct from episode-specific guests and crew. **Work package G.**

The Home, Watch, and detail navigation, owned-only episode lists, playback, user artwork overrides, and TMDB movie behavior remain as they are. This plan does not add provider-catalogue episodes to library ownership, change TV episode numbering automatically, create person credits from broad enrichment links, or turn the mockups into a separate editor application. Observable completion means an administrator can connect both services, match a season and one episode independently, see their correct images and attribution, refresh each from its recorded source, and open complete primary person details for the Solo Leveling fixture.

## Implementation and release status

The local implementation now includes user-supplied TMDB and TVDB credential setup, a direct TVDB v4 client, TVDB-only new television matching and artwork, independent season/episode editor matches, managed show/season/episode artwork, TVDB attribution, and provider-ID fallback for people without Wikidata QIDs. Focused API, provider, and Dashboard tests and a full solution build pass. The attached episode chooser informed the editor layout; it was not treated as authority to change episode numbering.

Release still requires an approved TVDB access model for self-hosted installations and an artwork-rights review under the current TVDB terms. A live account was not supplied in this workspace, so actual TVDB responses, the Solo Leveling library fixture, and desktop/mobile visual behavior need a connected acceptance pass before release. These checks are listed in Delivery and acceptance below.

## Findings that shape the work

- `config/providers/tmdb.json` classifies TMDB as `built_in`: its required `api_key` is `application_managed`, while the visible `api_key_override` is optional. `SetupProvidersStage.razor` groups providers using user-supplied fields, and the shared onboarding form renders only those fields. This explains why setup can treat an existing provisioned key as sufficient and never visibly request a TMDB key. The application-managed key path must be removed; the fix also needs a visible configured-credential review state, not secret disclosure.
- Before the TVDB-only routing change, the TV pipeline also selected TMDB for identity and images. `ImageEnrichmentService` and the editor artwork bridge could use a TMDB show ID, which allowed a legacy TMDB match to drive television refresh. The new routing must prevent that fallback while keeping stored artwork visible.
- `SharedMediaEditorShell.razor.cs` sets `CanMatchCurrentTarget` to episode-only for TV. `CanonicalCandidateBuilder` and the item canonical endpoints already guard against applying an episode from a different TMDB show. Season matching requires a typed season target and equivalent show/numbering validation; changing a season must not cascade an episode identity change.
- TMDB TV enrichment takes only the first 30 aggregate cast members in `ConfigDrivenAdapter.TmdbEnrichment.cs`. `PersonEnrichmentWorker` tries QID-first enrichment and then name reconciliation. Multiple downstream people readers cap results at 24. The exact Solo Leveling failure point is unproven until a representative claim-to-detail trace is run; the implementation should fix the measured loss rather than assuming one cap is the entire cause.
- The attached images are visual references for an episode match chooser and confirmation tray. They show TMDB and a season-to-episode numbering mismatch. The new flow should retain the useful layout and interaction, substitute the actual selected provider, and make source/target numbering schemes explicit. A screenshot is not evidence that a particular episode should be remapped.

## Provider access and attribution decision

TVDB v4 uses `POST /login` with an API key and, for a user-supported project key, a subscriber PIN; the resulting bearer token is used for subsequent requests. Its API keys are issued to projects rather than individual end users. The setup must accept an administrator-supplied project key that is approved for this installation and, when that key's model requires it, a subscriber PIN. It must not ship a Tuvima key, request one from a Tuvima proxy, instruct every household user to register an independent application key, or share one subscriber PIN among users. Before release, verify that TVDB permits the intended bring-your-own-project-key use for self-hosted installations and specify the accepted licensed/user-supported flow in the wizard. If that model is not permitted, leave TVDB disabled and explain why; do not work around the restriction with a bundled key. A self-host administrator who is also the project developer can follow the TVDB application link when that use is covered by their own approved key.

TVDB says end users viewing its API metadata need attribution with a direct link to TheTVDB.com unless TVDB has approved another arrangement. Store source IDs/URLs per fact and asset so the show, season, episode, person, artwork picker, and search/detail previews can render truthful attribution. Use TVDB's approved brand asset and wording after review. The API terms separately say API access does not itself grant rights to use or display third-party images; release review must verify the applicable rights/terms for artwork use before enabling TVDB downloads. These are release dependencies, not reasons to defer the local code and tests.

Official references: [TVDB API and attribution](https://thetvdb.com/api-information), [TVDB v4 API](https://thetvdb.github.io/v4-api/), [TVDB key models](https://support.thetvdb.com/kb/faq.php?id=81), [TVDB terms](https://thetvdb.com/tos).

## Technical work packages

### A. Provider catalogue and setup experience (walkthrough 1)

- Add a TVDB v4 provider definition, catalogue identity/icon, Watch applicability, setup instructions, troubleshooting, and a read-only credential probe. Add TVDB to setup, Settings, diagnostics, health reporting, and the test provider registry. Show TMDB even when its key is already configured; display a masked “key supplied for this installation” state with Replace/Test actions. Never return the secret to the Dashboard.
- Change TMDB's required `api_key` to `user_supplied`, remove `application_managed` and optional `api_key_override` behavior for TMDB, and require an administrator-provided v3 key on a fresh installation. Rework onboarding to guide the administrator to TMDB's key page and to review or replace an existing key. Migrate a previously user-supplied key from the legacy config/override into the installation secret store without exposing it; legacy values of unknown origin must be shown as needing administrator review before being accepted as the installation credential. Resolve one effective credential in the Engine and show its source/status, without using `Configured` alone as proof of successful connection. Do not force re-entry of a known user-supplied key restored from backup.
- Audit all keyed providers and startup/config defaults for bundled or application-managed secrets. Keyed functionality must fail closed with a useful setup/Settings repair action when its installation credential is missing; the application must never fall back to a Tuvima proxy or hard-coded credential. Public providers that require no key continue to work.
- Extend setup completion/readiness to report which Watch provider is active and what TV matching/artwork capabilities are unavailable when TVDB is deferred. Show historical TMDB TV records for review, without offering TMDB as a TV fallback.

### B. TVDB client and provider routing (walkthrough 1, 4)

- Implement a typed TVDB v4 HTTP client with login/token refresh, administrator-supplied project key and optional PIN handling according to the approved access model, cancellation, bounded retry/backoff, caching, rate limiting, and error classification. Keep tokens and credentials out of URLs, logs, diagnostic payloads, and browser storage. Connect directly from the local Engine to TVDB; no Tuvima proxy or embedded key participates. Use API responses and stable IDs from search/remote-ID, series/extended, season/extended, series episodes by explicit season type, episode/extended, people/extended, and artwork endpoints as supported by the approved account.
- Add TVDB to provider configuration, pipeline registration, provider health, and bridge-ID normalization. TVDB is the only retail provider for new TV show/season/episode resolution; TMDB remains the movie provider. Store the selected provider and exact show/season/episode ID per scope. Do not infer TVDB season or episode IDs from a TMDB number or title alone.
- Enforce the TVDB-only policy in editor search, apply endpoints, fresh ingest, artwork discovery, and refresh, even when an older local pipeline still lists TMDB. When TVDB is unavailable, keep the TV operation pending or return a clear skip; never apply TMDB as a TV fallback. Keep TVDB aired/DVD/absolute ordering separate; season 0 remains Specials, and an unknown season stays unknown.

### C. Typed match and persistence contract (walkthrough 2, 4)

- Extend the editor/API scope model so show, season, and episode have independent retail match identity, source, external ID, confidence, and revision. Add season ID keys and episode ID keys without collapsing them into `tvdb_id` at the show. Migrate existing TMDB identities in place without declaring them TVDB matches.
- Add scoped season candidate search and apply endpoints, plus provider-aware episode candidate browsing under the confirmed show/season. Validate authorization, show parent ID, level, numbering scheme, and optimistic revision at apply time. Return a preview of fields/artwork and a source-to-target map. Applying one level changes only that target's identity and provider-managed facts; local file placement, sibling episodes, custom artwork, and the show canonical identity remain intact.
- Keep the current conflict guard's intent for TMDB and add TVDB equivalents. If a candidate belongs to another show or numbering scheme, offer the existing explicit move workflow or stop with a useful error. Never silently remap Solo Leveling S2E1 to a local S1E13 merely because a title is similar.

### D. Editor presentation (walkthrough 2)

- Build one reusable candidate picker for show/season/episode, with provider labels and level-specific previews. For season selection, show numbered season, poster/background if available, dates and known episode range; for episode selection, implement the mockups' dropdown, filter, artwork rows, selected state, and pinned confirmation tray. Search is cancellable; list virtualization/paging keeps long seasons reachable.
- Use the shared `AppSelect`/control styling, existing editor panel tokens, keyboard focus, screen reader labels, and responsive layout. Make source and target IDs/ordinals readable in the confirmation tray and label the action “Match season” or “Match episode.” A user can cancel without writing. Season cards do not borrow episode stills, and an episode match changes only the owned episode.

### E. Managed artwork and correct refresh (walkthrough 3, 4)

- Adapt TVDB artwork records to existing `EntityAsset`, image download, variant generation, deduplication, preferred-selection, and responsive rendition helpers. Map TVDB show background/poster/clear logo to show slots, supported season poster/background to the season owner, and episode image/still to the exact episode owner. Inspect TVDB artwork type IDs and dimensions from real API fixtures before finalizing mappings; absent types remain absent rather than substituting another scope's image.
- Route TV editor Refresh artwork and scheduled re-enrichment through confirmed TVDB scope IDs only. Legacy TMDB TV artwork remains stored but is not fetched again; movies continue to use TMDB. Record provider, source URL, remote artwork ID, language, retrieval time, and scope. Preserve user-selected preferred art and image sizing contract; refresh can add variants without replacing a custom choice.
- Verify show and season images actually arrive, episode stills are owned-only in library surfaces, logos remain transparent where supplied, and the right bounded renditions appear on desktop/mobile. Add a diagnostic result identifying provider, scope, endpoint class, image counts, and skip reason without secrets.

### F. Source attribution (walkthrough 3)

- Add a shared attribution model/renderer for TVDB-sourced text and art, including a direct TVDB record link when available. Show it in detail/editor contexts and any other surface that displays TVDB data; audit cards and previews for source information without cluttering every tile. Mixed TMDB/TVDB fields must be attributed by actual source, not by the item's primary match badge.
- Include attribution in artwork picker and source/history screens. Test source switching, missing URLs, external-link safety, mobile visibility, and no attribution for purely local facts. Have the final wording/logo placement checked against the approved TVDB terms before release.

### G. Solo Leveling people remediation (walkthrough 5)

- Add a reproducible fixture from approved provider responses and trace counts through claim extraction, canonical arrays, reconciliation, person creation, enrichment queue, managed portrait acquisition, credit persistence, and detail projection. Compare show aggregate cast, episode guests, eligible crew, and stored people; identify where each missing person is lost. No live user's API secrets or personal database are needed in test fixtures.
- Preserve stable TVDB person IDs for television and TMDB person IDs for movies, with role/character evidence when supplied. Enrich a provider-ID-linked person directly when no QID exists; use Wikidata reconciliation as optional identity evidence, with ambiguity held for review rather than a wrong merge. Retry incomplete profiles, respect source language, and keep user edits. Remove truncation in the durable ingestion path; retain bounded UI previews with an explicit full credits path. Only canonical primary contributor arrays/claims determine browse/search/person works, consistent with the current product rule.
- Test Solo Leveling and a non-anime show for missing QIDs, multi-role people, translated names, show versus episode guests, portrait fallback, and re-enrichment. Confirm the person detail route opens with sourced facts or an honest “details unavailable” state.

## Delivery and acceptance

1. Ship A and the approved credential model in B first, with setup/Settings tests for fresh, restored, invalid, rotated, and missing keys. Assert a fresh installation contains no TMDB or TVDB key, makes no keyed provider call before entry, and never contacts a Tuvima proxy. TVDB cannot be called until valid access is configured.
2. Implement B and C with recorded provider identity and season-type safeguards; run contract and migration tests on existing TMDB TV data. Then implement D against those contracts.
3. Implement E and F together so no TVDB image or text is presented without provenance and attribution. Verify real API fixtures for show, season, episode, artwork types, pagination, missing art, token expiry, and throttling.
4. Implement G from the trace results, then run a disposable fresh ingest and a re-enrichment of an already matched fixture. Validate owned-only counts, image `currentSrc`/scope, people details, editor behavior, and source attribution at desktop and mobile sizes. Run solution restore/build and the focused API, provider, storage, and Web tests; capture rendered editor before/after states.

Release acceptance: TMDB and TVDB are both visible in setup regardless of pre-existing credentials; every required key is supplied by the installation administrator rather than shipped with Tuvima; no secret is exposed and no Tuvima proxy is needed; TVDB is the only source offered or applied for new TV identity and provider artwork; season and episode matches are independent and reviewable; all available show/season/episode art uses managed services and the correct owner; TVDB attribution is visible with a direct link; and the Solo Leveling fixture's primary people have explainable, accessible details. If TVDB bring-your-own-key access or image rights are not approved, keep the integration disabled in release configuration and state the unavailable capability in setup.

## Plain-English completion summary

This plan requires the administrator to supply the TMDB and TVDB credentials used by their installation, with no key built into Tuvima or proxy dependency. TMDB serves movies; TVDB alone supplies new television matches and provider artwork. Seasons get their own match and artwork, and legacy TMDB television records remain visible until an administrator rematches them to TVDB.
