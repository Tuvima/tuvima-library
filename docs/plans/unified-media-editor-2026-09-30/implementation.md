# Unified media editor implementation ledger

## Product walkthrough

1. **Pick owned files in one place.** The existing editor keeps its Details, Artwork, Match & Identity, and History destinations. A compact file pane holds the checked file set while the user moves among them. Focusing a row only changes what is inspected; checking files defines a proposed action's selection. A single-file title remains visually simple. **W1, W2, W4.**
2. **Match a parent and review every proposed child.** For a show or exact album release, the user chooses the parent, sees episode or track proposals for the checked files, resolves ambiguity, and saves accepted rows together. A correction to one file follows the same review path. Ordinary browse, playback, and detail routes remain as they are. **W2, W3, W4.**
3. **Edit artwork at its owner.** A show poster, season poster, exact release cover, episode still, and edition cover may have different owners. The editor displays which owner changes and how many owned files inherit it. Changing a group preference is staged until Save and does not create a special subgroup for the checked files. **W1, W2, W5.**
4. **Save once, then see file outcomes.** The Engine validates the complete reviewed plan, commits library state and durable work intents, and synchronizes permitted files afterward. The UI reports verified, pending, policy-blocked, unsupported, and failed outcomes without treating a catalogue result as owned media. **W2, W4, W6, W7.**
5. **Recover only what was written.** Later ingestion reads supported scoped IDs, ordering, facts, and artwork from the physical file. The app distinguishes offline restoration from a fresh provider confirmation. Unwritten provider context and personal state are outside the offline guarantee. **W1, W6, W7.**

Observable acceptance includes a single asset; several assets for one Work; several meaningful Editions for one Work; several assets in one Edition; a TV episode with two versions; original and deluxe music releases; and one ambiguous multi-episode file left in review. Desktop, tablet, and mobile layouts must keep the selection, inspector, and Save/Discard controls readable without overlapping content.

The supplied TV and music Match screens define the main interaction: a checked file list on the left, an exact parent identity above a readable child-mapping table, explicit per-row review, and an always available selection count and Save/Discard area. The movie and TV Artwork screens define a compact role switcher and candidate images with one clearly preferred choice. The screenshots are reference compositions rather than proof that their displayed titles, percentages, file counts, or artwork are present in the user's library.

## Scope and input authority

The supplied `tuvima_media_editor_codex_plan.md` is the requested implementation specification. The edition-aware pasted addendum extends it. The four screenshots are layout and content examples: sample titles, counts, and match states are not fixture evidence. This ledger tracks code and verification; it does not turn either attachment into a separate user request.

Existing browse, playback, detail routes, permissions, canonical identity, source mutation policy, and configured sidecar export remain in scope as compatibility constraints. This work does not add transcoding, splitting, general hierarchy drag-and-drop, automatic quality ranking, or a preferred playback-version feature.

### Target ownership matrix

| Media | Structural owner | Work owner | Edition or release owner | Asset owner | Default artwork owner |
| --- | --- | --- | --- | --- | --- |
| Movie | optional series | film identity and provider movie ID | supported cut/release distinction | file path and measured technical facts | film Work, optional Edition override |
| TV | show and season | episode identity/number | optional version | file and technical facts | show poster/background/logo, season poster, episode still |
| Music | release-group context | recording and release-track context | exact MusicBrainz release | audio file | exact release when actually modeled; current album Work otherwise |
| Book | optional series | literary identity and series order | ISBN, publisher, translation, edition date | ebook file | Edition |
| Audiobook | optional series | literary identity | narration/release, ASIN, cover | part file and embedded chapter structure | Edition |
| Comic | run/volume | issue identity | optional printing/variant | comic file | issue, optional Edition override |

The current database does **not** yet realize every target cell. In particular, a per-file technical Edition is not an exact music release. The read model reports current effective ownership, while any ownership migration needs a separate data repair and acceptance test.

## Decision and risk ledger

1. **Model availability:** The worker tool in this Codex session does not offer Terra. Available workers are assigned disjoint files under Sol orchestration; model substitution is reported to the user.
2. **Frozen selection boundary:** The all-matching endpoint returns explicit IDs and revisions up to 1,000; the Match UI preserves them, and preview requires complete revisions. New files do not join a reviewed operation, and the existing blanket batch mutation endpoint is not used for parent-first matching.
3. **No client-authored identity commit:** Episode title/number, release, and parent links must be verified by the Engine against provider or established local evidence before the database transaction. The TV HTTP Save now accepts only an actor-bound review token, accepted provider episode IDs, exclusions, and an operation token; catalog-only targets are rechecked for zero actual assets in the transaction.
4. **Writer capability:** Existing `.mkv` handling cannot be promoted to complete scoped Matroska write support without a writer spike and independent file read-back. Unsupported and unavailable are separate outcomes.
5. **Data repair:** Existing wrong asset/work claims and per-file technical Editions require an auditable dry-run before bulk migration; future-only routing changes cannot repair them.
6. **Cross-show correction:** The current verified TV transaction encodes one show and checks source and target under that show. A cross-show Save needs a dual-show operation that recalculates ownership for both roots and their seasons, rechecks both shows' artwork impact, and authorizes every target owner and library. The existing guard rejects such a move without mutation; its focused negative test passes. Preview may show a different show, but it is read-only until this transaction exists.
7. **Exact music release-track identity:** The provider manifest now preserves Track MBIDs, but local target Work/Edition bridges do not persist a release Track MBID or a proven release-scoped target. One Recording MBID can occur in multiple releases with different positions. A future migration must persist the release Track bridge, Edition release ID, Edition-scoped disc/track, and separate Recording ID from provider-confirmed evidence; ambiguous legacy Editions remain unsaveable. Preview no longer treats an album Work release ID as Edition evidence.

## Plain-English completion summary

The editor now keeps one checked file set across sections, shows real Edition relationships and inherited covers, reviews parent-first matches, and lets users save accepted same-show TV episode corrections with one episode still and one show or season artwork choice together. It checks every affected owned file, prevents a partial library commit on conflict, and queues all affected files for synchronization. History follows the checked files, while internal navigation warns about unsaved edits. Supported fields in MP3, M4A/M4B, MP4, FLAC, OGG Vorbis, EPUB, and CBZ receive physical read-back verification; other fields and formats remain explicitly unverified. The broader Details and Artwork controls still have separate commit behavior, music release-track and cross-show TV Save are unavailable, Edition cover editing is read-only in the public editor, and full offline re-ingest and browser visual acceptance have not been proven. The implementation remains a partial delivery against the supplied plan.
