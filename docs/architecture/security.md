# Security Architecture

## In this page

Live account, profile, application, and resource authorization in Tuvima Library.

## Where this lives in the code

- `src/MediaEngine.Identity`
- `src/MediaEngine.Api/Security`
- `src/MediaEngine.Admin`
- `src/MediaEngine.Web`

This describes the Access implementation under final integration. Delivery evidence and remaining acceptance gates are recorded in the [Access execution status](../../engineering/plans/access-architecture-2026-09-08/execution/status.md). The replacement is accepted as one cutover; individual worker checkpoints do not represent deployment.

## Accounts and profiles

An account authenticates a person and owns Read, Watch, Listen, View, actual catalogued-library grants, and administrator eligibility. A profile owns experience, restrictions, history, and Personal Space identity. Each account may hold at most eight profile grants. Sharing a profile deliberately shares that profile's experience and private space; it does not transfer another account's administrator eligibility.

Effective administration requires an enabled account, a valid active account/profile grant, account administrator eligibility, and `AdminEnabled` on that grant. An optional grant-specific PIN protects administrator surfaces independently of sign-in and profile-selection PINs. Unlock expiry and authorization revisions are enforced by the Engine. The Dashboard consumes projected navigation/actions and never trusts a locally stored profile role or a seed-owner fallback. Editor entry uses the shared unlock prompt and revalidates before opening.

There are two administrator levels. A **server administrator** runs the Engine: server settings, folders, network, inviting new households, and every household. A **household administrator** looks after one household only: adding and removing its people, giving them their own sign-ins, resetting their passwords and two-step codes, PINs, and handing out libraries and features that the household's main sign-in already holds (never more). A household administrator can never act on a server administrator or another household administrator, turn on administrator access for anyone, or reach another household; the Engine answers a lookup of another household's account as "not found". The flag lives on the account (`accounts.household_admin`) and only a server administrator can change it; someone invited from outside as a new household becomes that household's administrator. Household administration needs a person who is not on a child profile. A household administrator can turn on an administrator PIN for their own household administration (never for anyone else's); once on, it must be unlocked like a server administrator's. They cannot change the person another administrator signs in as, and the profile PIN route accepts people only, never applications. The first server administrator joins the household that already holds the server's Shared Library rather than starting another. Each household has its own Shared Library, and a contribution always lands in the submitter's household library.

An account needs an email only when it can be used away from this computer: when a password or passkey is set, when an own sign-in or invitation is created, or when an outside sign-in is linked (the provider's email is used when it supplies a usable, unused one; otherwise the request must carry one, which no Dashboard screen offers yet). The one exception is the this-computer account made at setup, which has only a name and works only on that computer until it is secured; `accounts.email` and `normalized_email` are nullable for it. An account without an email cannot sign in with an email, use email recovery or be invited by email (recovery codes still work once it is secured), and the screens show *No email* for it. There are no email-less "local-only" accounts and no sign-in by Profile ID: a person without their own sign-in is a profile in someone else's household, opened by switching profiles (guarded by the profile PIN when one is set). At startup, a data store from before this rule has each email-less account's profiles moved into the server administrator's household and the email-less account removed; if that would exceed eight profiles, startup stops with a message naming the profiles and the `tuvima-admin` recovery step instead of dropping anything. A localhost request alone is never an administrator identity. Public setup, authentication, recovery, and health routes are explicitly designated exceptions; other endpoints require an authenticated authority and the applicable operation/resource checks.

## Applications and native clients

Applications own registered service permissions. Their credentials are hashed, independently revocable, and shown once when created. Rotating a credential does not change Application permissions. `X-Api-Key` resolves the live Application and exact credential rather than a role embedded in a key.

Server integrations and automation act as service principals. User clients additionally bind the current account, active profile grant, device, consent, and native token. Effective delegated access is their intersection. Disabling an account, grant, Application, credential, device, or token must revoke dependent access. The Dashboard service identity only authorizes its narrow transport duties; it cannot substitute for the signed-in human.

**Switching person on a paired device.** A paired app (a phone or television) switches profile without re-pairing through `GET /api/v1/devices/current/profiles` and `POST /api/v1/devices/current/switch-profile` (`DeviceProfileSwitchService`). Only the paired app's own bearer token for a live device of its own account may call them: a Dashboard session, another account's token or a service credential is refused with `403`, even when it carries the device id. The people offered and accepted are the profiles the device's account holds an enabled grant for, the same check the Dashboard's `POST /auth/session/switch-profile` makes. The PIN goes through `IProfilePinVerifier.VerifyProfilePinAsync`, the Dashboard switch's own check, and is asked at every switch, so a Kids profile cannot hand the device back to a PIN-protected person without it. Wrong PINs always count toward the profile's lockout (5 failures lock it for 15 minutes), as for any app. A refused switch changes nothing and writes no audit entry. The grant is checked before the profile is looked up, so an id that does not exist and one the account cannot use both answer `403 profile_not_allowed`. A missing or wrong PIN answers `428 pin_required`. Both actions share one allowance of 30 a minute per device (`DeviceActionThrottle`, a bounded in-memory table that drops devices idle for a minute). It is keyed by the device, not the token, so rotating tokens never buys a new allowance, and it is only consulted after the Engine has verified a live paired device of the caller's own account, so made-up bearer strings or forged device ids allocate nothing. Over the allowance answers `429 rate_limited` with `Retry-After`. Switching to the person the device is already using answers `409 already_active_profile` before anything else is checked, so a switch cannot be looped just to mint tokens. A switch re-checks everything a refresh does (account, the new profile's grant, Application and its scopes), then in one transaction rebinds the device to the new profile, revokes every token the device holds (reason `profile_switched`) and stores a new access and refresh pair in a new token family, so one device never has two live profiles and the previous refresh token cannot be used again. The transaction only goes ahead while the device is still on the profile the caller authenticated as and the caller's own access token is not revoked, so of two switches made at once exactly one succeeds. Token lifetimes, the device id and the approved scopes do not change. Each switch writes the audit event `device.profile_switched` (actor account, the new profile, subject device, `from_profile_id` as the caller authenticated and `to_profile_id`; never the PIN) in that same transaction, so a switch is never stored without its audit entry and a failed audit write undoes the switch. Wrong profile PINs are limited in the data store, not from a snapshot read in memory: each guess first reserves an attempt with one conditional `UPDATE` (matching no row while the profile is locked or already has 5 attempts outstanding), and a guess that reserves nothing is refused without being checked. A right guess clears the count only while no lock is running, so a burst of parallel guesses cannot exceed 5 checks or undo a lock it just set, and a lock that has run out starts the count again at 1. This is the shared path the Dashboard switch, profile sign-in and phone backup also use. The new profile's content limit applies from the next request because the limit is read live for the token's active profile.

**Photos and personal videos for paired apps.** The three scopes `view.personal.read`, `view.originals.read` and `view.galleries.read` (`ApplicationPermissionIds.NativeClientPhotos`, `ClientApiScopes.Photos`) are in the set an app may request but never in the defaults or the Media Player preset, and they are granted only through the person's own explicit consent. The Dashboard's `/pair` screen lists them as one separate item, **Allow access to my photos and videos**, unticked by default; the Dashboard turns that single tick into the three scopes in the decision, and a photo scope posted as an ordinary scope field is dropped. `ClientAuthorizationService.DecideAsync` never grants them from a decision that omits `scopes` and still intersects every decision with what the app requested, so a person who leaves the item unticked, an older Dashboard, or a direct caller approving with no scopes cannot grant photo access silently. An app gets only what the person approves: `PairingDecisionRequest.scopes` omitted (null) means every requested scope except the photo scopes, an explicit list means exactly that list, and an approval that leaves nothing to grant (an explicit empty list, or one naming nothing the app asked for) throws `ArgumentException` and the decision endpoint answers `400` before anything is stored, so no device that can do nothing is created. The `/pair` form always sends an explicit list and refuses an approval with nothing ticked on the Dashboard's server (the screen shows "Choose at least one thing this device may do, or deny the request." with status `400` and never calls the Engine). The photo scopes also need the requesting Application to hold them: `PairingReviewResponse.offers_photo_scopes` (the Application is enabled, is the bound user client and `HasEffectivePermissionsAsync` holds for all three) decides whether `/pair` shows the photo item, and `DecideAsync` refuses a photo scope for an Application without the grants with `400`, so a crafted post cannot create a device that would fail at token exchange with `access_denied`. Re-pairing is the only way to change the photo choice; removing the device ends its photo access at once. Removing any one photo grant from the built-in Application later signs out every device that opted in (token validation re-checks the Application grants for every scope on the token), so they must pair again. On existing data stores the one-time `access_native_photos_seeded` seed added the three photo grants to the built-in Application even where an administrator had trimmed its permissions; they are inert for a device without that device's own per-pairing consent. Both layers must hold them, as for every Application permission: the built-in native-client Application (granted once at startup by the `access_native_photos_seeded` marker, so later administrative removal sticks and a deleted Application is not recreated) and the device token's own scopes (`HasDelegatedConsent` reads the token claims, `EvaluateApplicationPermissionAsync` reads the Application grants). Revocation is the existing device revocation: the device's tokens stop validating at once, so its photo access ends with it (`401`); an Application that loses the scopes stops serving existing devices too. A device paired before the scopes existed, or one approved without the item, gets `403` on every `/api/v1/view` route. Resource rules are unchanged: only the active profile's own photos and videos and Galleries shared with that profile, documents answering `404` as for an unknown id, no write verbs. The Dashboard's app door (`NativeApiForwardPolicy`) passes exactly the eleven `GET` view routes and nothing else under `view/`.

Interactive Dashboard clients use `DashboardCircuitHttpClientFactory` to forward the current circuit's session outside the pooled HTTP-handler scope. The existing handler pipeline still resolves the protected service credential at send time. A cleared established session suppresses stale ambient-request fallback; an explicit identity-validation token remains a separate supported request. Client configuration and pooled transport lifetime remain owned by the normal HTTP factory.

Profile loading initializes the existing principal and awaits validated authority before its first request. Empty failures remain retryable, and delayed results cannot publish after session identity or access changes. Repeated validation with equivalent authority does not emit a false change event or cancel active playback tools; genuine session, grant or capability changes retain the revocation path. The live refinement evidence is recorded in [the implementation report](../../engineering/reports/audiobook-refinement-2026-10-02.md).

`TuvimaAuthentication` establishes identity; `IRequestAuthorityResolver` resolves current authority; `IAuthorizationEvaluator` decides registered operations. Endpoint metadata exposes those decisions for mapped-route guardrails. A valid credential alone is insufficient to authorize an operation.

## Resource scope

Catalogue access applies feature and actual library grants to concrete assets before representative selection, counts, grouping, pagination, and serialization. Every artwork, download, reader, HLS, queue, history, bookmark, and progress path verifies its resource independently. Multiple assets of one work do not let an allowed library reveal another library's variant. HLS grants retain exact live authority bindings, and personal writes require the current profile.

A browser reader needs the book file itself, and a browser cannot attach the Engine's credentials. The Dashboard route `/engine-book/{assetId}/file` (`EngineBookProxyEndpoint`) therefore fetches `GET /read/{assetId}/file` for the signed-in person. It is deliberately narrower than the artwork proxy: exactly one asset id in canonical form and one fixed suffix, parsed strictly and rebuilt into the Engine path, so a request can never be steered to another Engine route, and the query string is never forwarded. The Engine call goes through the normal Engine client, which resolves the Dashboard's credential at send time and forwards the person's session, so the Engine still decides library grant, feature and profile content limit; a missing or unreadable credential fails closed, and a signed-in cookie that carries no Engine session answers `401` without calling the Engine at all (the Dashboard's own credential is never used on its own to read a book). Book reads have their own `reader_files` rate limit, counted per signed-in session rather than per shared Dashboard address (`ReaderFileRateLimitPartition`; `rate_limiting.reader_files` in `config/core.json`). Only `Range`, `If-Range`, `If-None-Match` and `If-Modified-Since` cross to the Engine, and only content type, length, range, validators and `Retry-After` come back. An Engine refusal and a missing book both read as `404`, so a browser cannot probe which books exist; other Engine failures read as `502`. The Engine route serves only reading formats (`.epub`, `.cbz`, `.cbr`, `.pdf`), never video or audio, even to someone who may read the library. Responses are `private, no-cache` (every use is authorised again), `nosniff` and sandboxed (`Content-Security-Policy: default-src 'none'; sandbox`) because the file is user content that must never run as a page on the Dashboard origin.

View has its own feature and resource policies. Private access resolves the exact active profile. Explicit administrator inspection remains a separate scope. Shared Library access, contributions, review, and Gallery sharing remain separate policies. A Gallery share authorizes proven Gallery members and derivatives, never sibling assets or an entire private source. View assets never enter catalogue provider enrichment. Deleting identity records must not delete original media or transfer a private space to another person.

## Open screens

An open Dashboard screen is a Blazor circuit that never sees a new HTTP request, so it follows access changes by two routes.

- **One-minute check (the backstop).** `SessionRevalidatingAuthenticationStateProvider` asks the Engine once a minute whether the screen's sign-in still stands and re-applies the door rule to the place the screen was opened from (`ExposurePolicy` against the current "who can connect"). The same call refreshes what the person may do, so there is at most one Engine validation per open screen per minute and none per page interaction. A revoked, disabled or wrong-place sign-in turns the screen anonymous and `SessionEndedRedirect` (in every layout a signed-in person can reach) sends it to `/auth/login`. An Engine hiccup (timeout, throttling, restart) never signs anyone out; only a proven invalid sign-in does.
- **Instant for big changes.** `OpenScreenCircuitHandler` registers each signed-in circuit in the singleton `OpenScreenRegistry` (account, profile, session, a hash of the session token, and the place it was opened from) and removes it when the circuit closes. After the Engine confirms the change, the Dashboard calls `CloseWhere` so matching screens go to sign-in at once: lowering "who can connect" (screens from farther away), removing or disabling a person, removing a profile or a profile grant, signing out a device, and signing out other sessions (the kept session stays open).

Not covered: media already streaming (it uses short grants) and Engine-pushed session events.

## Authentication and recovery

**Network location is not checked.** Where a visitor connects from never decides whether they are let in. `ExposurePolicy.Evaluate` always allows, `IngressClassifier` reports `this_computer` only for a direct loopback connection (not one on the proxy port or relayed by a configured proxy) and `home_network` for everything else, `ClientIngress.Parse` maps every other value to `home_network`, `AuthenticationEndpoints.AllowsClient` only checks that the method is enabled, apps are admitted whenever app access is on, and `SecureAccountGate` never refuses. Account lockout and the profile PIN limit apply to every attempt wherever it comes from (5 failures lock the credential for 15 minutes). A passwordless account can be used from any device that can reach the port, so adding a password is the only protection once the port is shared. The **Who can connect** setting, `issued_ingress` and `this_computer_only` still exist in the data store and settings screens but restrict nothing.

Settings → Users & Access contains Households, Applications, and Authentication; people, PINs and their own sign-ins are looked after from each person's page under Settings → Profiles. Authentication controls local passwords, passkeys, invitation policy, session policy, and external providers. Readiness is derived from real configuration; unavailable sign-in methods carry reasons. Verified external identities use provider, canonical issuer, and immutable subject. Email alone never silently links an identity. See [external authentication](../guides/external-authentication.md).

**Everyone's sessions.** Settings → Administration → Devices lists and ends other people's sessions through `GET /access/sessions` and `DELETE /access/sessions/{sessionId}` (`ManagedSessionService`). The scope is decided in one place: a server administrator reaches every account, a household administrator reaches accounts of their own household except server administrators and other household administrators (the same protection `RequireNotAdministratorTarget` gives their sign-ins elsewhere), and anyone else or any app is refused with 403. Ending a session needs a recent sign-in, refuses the caller's own session with 400 (it is ended with Sign out), is audited as `account.session_revoked_by_administrator`, and closes the Dashboard screens open on that session. The self-service endpoints (`/auth/sessions`) are unchanged. Members who are not administrators no longer see Sign out everywhere else or the Devices link on Security, and paired devices moved from Security to the Devices page.

**Starting without a password.** Setup can start with just a name (`POST /setup/v1/administrator` with `sign_in = this_computer`; the email field is not asked for and is ignored). The account has no password credential and `accounts.this_computer_only = 1` (`Account.IsThisComputerOnly`, changed only through `MarkThisComputerOnly`/`ClearThisComputerOnly`). To come back later without a password the Dashboard's `GET /auth/login` asks the Engine (`GET /auth/this-computer`) and, when it names the account, signs in with `POST /auth/this-computer` and goes straight in: to the profile picker when the account has several profiles (`choose_profile`), otherwise to Home, with no sign-in page (`DashboardAuthenticationEndpoints.StartWithoutPasswordAsync`). That means `GET /auth/login` can sign a visitor in without a click, which is accepted because it applies only to the single passwordless setup administrator. An explicit sign-out redirects to `/auth/login?signedOut=1`, which skips the automatic sign-in and offers a single *Go back in* button. The Engine still refuses `/auth/this-computer` for a request that arrived with `X-Forwarded-For`/`Forwarded` or that the Dashboard marked with `X-Tuvima-Client-Forwarded: true`. Once an administrator has a password or passkey the account stops being offered and the sign-in page is shown as normal.

**Sessions record where they started.** Every session stores the place it was made from (`this_computer` or `home_network`) in `auth_sessions.issued_ingress`, for audit only. It no longer limits where the session works.

**One sign-in check per burst of requests.** A page load fetches dozens of scripts, styles and images from the Dashboard, and each carries the sign-in cookie. `DashboardIdentityClient.ValidateCookieAsync` answers them from one Engine `POST /auth/session/validate` through `SessionValidationCache`: requests from the same session token, place (ingress) and Dashboard credential share one in-flight check, and a check that came back *valid* is reused for at most 5 seconds (never past the session's own `expires_at` or an administrator unlock's `administrator_unlock_expires_at`). Only valid answers are kept. A refusal, a throttled or unreachable Engine and a missing or unreadable Dashboard credential are never remembered and never answered from memory (the call goes out and the credential handler refuses it), and a rotated credential, another token or another ingress is a different key. Any call through the identity client that is not a read (sign out, switch profile, revoke a session or device, change access, password or protection) empties the cache before and after it (`SessionValidationInvalidationHandler`), and a check already under way when that happens is neither joined nor kept. The Engine still validates the session on every call it receives, and each open screen still re-checks every 60 seconds without the cache, so the only added delay is up to 5 seconds for a change made outside this Dashboard (for example host recovery) to reach the cookie check.

The administrator-console PIN stays optional: sign-in and profile switching never ask for it, and the unlock is requested only when entering administrator areas while protection is on. A restricted (child) profile never has administrator authority, even if its grant says `AdminEnabled`; the Engine refuses to set it and the Dashboard hides the toggle.

Administrator password recovery uses one-time recovery codes or the elevated host command:

```powershell
dotnet run --project src/MediaEngine.Admin -- auth reset-password --config-dir config
```

The command takes the password through a non-echoing interactive prompt, requires operating-system administration, and refuses to create a missing database. Recovery invalidates existing security credentials/sessions according to the account recovery service. There is no anonymous localhost password-reset bypass.

**Recent sign-in and securing an account.** Each session records `authenticated_at`. Sensitive actions (change password, add or remove a passkey, link or unlink a provider, replace recovery codes, sign out other sessions, set or remove a PIN) are refused with `403` and `code: "confirm_its_you"` unless it is within `RecentSignIn.Window` (10 minutes); `RecentSignInGuard` enforces this on the Engine and a missing session counts as stale. `POST /auth/confirm` refreshes it with the password or a passkey and respects credential lockout. A this-computer-only account has no secret to confirm with, so its `ThisComputer` sessions count as recent. `POST /auth/account/secure` lets that account add a password or passkey (and, when it has no email, the email to sign in with; `FirstPartyIdentityService.SecureThisComputerAccountAsync` normalises it, refuses one another account uses and stores it), clears `this_computer_only`, replaces recovery codes and revokes every old session; the Dashboard's `/account/secure` form issues the replacement cookie because Blazor circuits cannot set cookies. Changing a password no longer asks for the old one (the recent check replaces it), and no action removes a password. The last-method guard is unchanged.

**Two-step codes.** An account with a password can opt in to time-based one-time codes (RFC 6238: HMAC-SHA1, 30-second steps, 6 digits, one step of clock drift accepted either side) implemented in `MediaEngine.Identity/TotpGenerator.cs` with no extra library. The secret lives in `account_two_step.secret_protected`, encrypted with ASP.NET Data Protection (purpose `Tuvima.TwoStep.Secret.v1`), so copying the data store alone does not reveal it. `last_used_step` is advanced atomically, so a code works once even across devices. A row with no `enabled_at` is an unconfirmed setup. When two-step is on, `POST /auth/login` returns `202` with `two_step_required` and a pending token instead of a session. The token is random, stored only as a hash in `two_step_challenges`, lasts 5 minutes, works once, allows 5 wrong codes, and is bound to the ingress it was created for; presenting it from a different ingress ends it. `POST /auth/two-step/verify` accepts the 6-digit code or a recovery code and issues the session. Wrong codes follow the same lockout rules as passwords: only `remote` attempts count, and the password failure counter is not reset while a code is still pending, so repeating the password cannot restart code guessing. `POST /auth/confirm` also needs the code. Passkey and external-provider sign-ins skip the code by design. Turning it on, off and resetting are behind `RecentSignInGuard`. An administrator can turn it off for another account (`POST /access/accounts/{accountId}/two-step/reset`, audited as `account.two_step_reset`; a server administrator needs an unlocked administrator session to reset another administrator), and the host console command `tuvima-admin auth reset-two-step --email` does the same without a code and writes a `two_step_reset` identity audit event. Text or email codes, trusted devices and enforcing two-step for everyone are not part of this feature.

### Password rules

Account passwords need at least 12 characters (128 at most). The server refuses any password found in the bundled common-password list (`src/MediaEngine.Identity/Resources/common-passwords.txt`, derived from SecLists, MIT) and any password that equals the account's email address or the profile's display name, ignoring case. The rule runs when a password is created or changed: bootstrap, invitation accept, change password, recovery-code reset, reset-link reset and the host reset command. Existing shorter passwords still sign in. The Dashboard shows the same hint under each password field.

**Admin-created sign-ins, no self sign-up.** Only an administrator creates accounts (the first administrator is created by the setup session). `AccountCreationGuardrailTests` lists every source file that can create an `accounts` row and fails when a new one appears or when the administrator-only routes lose their `RequireAdministratorOrApplication` policy; linked sign-in never creates accounts. An administrator can hand over a new sign-in in two ways, and Tuvima sends no email for either. **Invitation code:** `InvitationCode` makes ten characters from `ABCDEFGHJKMNPQRSTUVWXYZ23456789` (about 50 bits), shown as `XXXXX-XXXXX`; only the SHA-256 of the normalized code is stored (`account_invitations.token_hash`), it works once and expires after `auth.invitation_lifetime_hours`. The Dashboard shows the code, the link `/auth/invite?code=…`, and an SVG QR code (QRCoder, MIT) once. Preview and accept answer an unknown, expired, used or disabled-account code with the same plain `404`/`401`, and wrong codes are counted by `SignInAttemptLimiter` (see the per-address limits below) and the Engine `authentication` limiter. **Temporary password:** `accounts.must_change_password` and `temporary_password_expires_at` (always 7 days). `PasswordChangeRequiredMiddleware` (after authentication) refuses every endpoint except `ChangeTemporaryPassword`, `ValidateAuthSession` and `RevokeAuthSession` with `403 password_change_required` when the session's account has the flag, and the Dashboard redirects every page to the full-page `/auth/change-password`. Changing it checks the temporary password, applies the normal password rules, clears the flag, revokes all of the account's sessions and issues a new one. Once it has expired, sign-in says "Ask your administrator for a new temporary password." (only after the password itself was right) and existing sessions stop validating. Choosing a password by any other route (reset, recovery) also clears the flag. Passkey enrolment is not offered on the invitation page; it is added afterwards in Account > Security.

### Sign-in limits

Three layers keep guessing in check without letting one person lock out everyone else:

- **The Engine only answers to loopback names.** Its `AllowedHosts` is `localhost;127.0.0.1;[::1]`, so a web page that rebinds a hostname to the user's machine (DNS rebinding) is refused with 400. The Dashboard (`Engine:BaseUrl` or `TUVIMA_ENGINE_URL`, which must therefore be a loopback name), the Docker healthcheck and the installer all use one of those names, and the Dashboard no longer forwards a visitor's Host header on passkey calls; a guardrail test fails if the setting goes back to `*`.
- **Passkeys belong to the public address.** `PublicAddressPasskeyOptions` sets the passkey relying-party domain to the host of `network.remote.public_hostname` and accepts only that exact origin, read again for every request scope so a changed address applies without a restart. With no valid public address no origin is accepted. The sign-in page therefore offers the passkey button (and the Dashboard accepts passkey option requests) only for a visitor who arrived at exactly that origin; anyone on localhost or a LAN address sees password sign-in only.
- **Pairing links ignore forwarded headers.** The device-pairing link is built from the public address when set, otherwise the Engine's own request origin; `X-Forwarded-Proto` and `X-Forwarded-Host` are never trusted. The Dashboard's app door then rewrites `verification_uri` and `verification_uri_complete` in the pairing response to the public address, or, with none set, to its own host-allow-listed request origin, so apps never see the Engine's loopback address.
- **The Engine treats the Dashboard as many people.** Because every Dashboard-forwarded sign-in reaches the Engine from the Dashboard's own address, requests carrying the Dashboard service credential get their own partition of the `authentication` policy (300 a minute, `AuthenticationRateLimitPartition`); the credential is recognised from memory so the limiter still runs before authentication. Any other caller keeps 10 a minute per address.
- **Account lockout counts every failure.** After 5 failures the password or PIN is locked for 15 minutes, wherever the attempts come from, because no per-address limit remains. A stranger who knows an email address can lock the owner out; that is the accepted trade-off.

## Plugin and event boundaries

Plugin execution receives host-bound identity and declared capabilities. External service permissions are separate from host capabilities. Unimplemented capabilities remain unavailable with a reason. The Fandom Lore service exposes one bounded typed operation with authorization before effects.

Application events use a dedicated `/application-events` hub and durable outbox. Envelopes contain `event_id`, `event_type`, `version`, `occurred_at`, `server_id`, `subject`, and `payload`; the server ID is a persisted opaque identity. Delivery rechecks the current principal and resource scope. Replay is bounded and reports gaps. Dashboard Intercom recipients also receive live account/resource checks. Its frozen Lore/Universe contract pair is unchanged; the reviewed ingestion event contracts add optional asset and pre-removal provenance fields so event authorization remains possible after deletion. Durable projection precedes best-effort Dashboard delivery, and one failed recipient does not discard the event or block other recipients. Exact live-connection and producer evidence is tracked in the execution status.

Webhooks belong to service Applications. Endpoint configuration, selected event permissions, and delivery are revalidated. HTTPS is the public default; explicit local-network approval permits private destinations. Loopback, link-local/metadata, redirects, proxy routing, mixed unsafe DNS answers, and DNS rebinding are rejected. Delivery signs the timestamp plus the exact UTF-8 body with HMAC-SHA256. Signing secrets appear once and are protected at rest. Retries retain a stable delivery identity, bounded queue, attempt count, and expiry; errors expose sanitized status without credentials or response bodies.

## Secrets, limits, and lifecycle

Provider definitions live under `config/providers/`; long-lived provider credentials belong in gitignored overlays under `config/secrets/`. Authentication provider secrets use their dedicated protected overlay. Credentials, PINs, passwords, invitation/recovery tokens, and webhook signing secrets must not enter logs or ordinary DTOs.

Rate limits apply to authentication, credential operations, streaming, general API access, and real-time connections according to the registered policies. Folder and managed-asset operations validate intended roots and provenance before disk access; authorization does not waive existing-source protection.

Pre-beta obsolete database/configuration state fails fast and is rebuilt from configured sources. Do not add compatibility authorization schemas, old role readers, or automatic key conversion. This permission covers disposable application state only; original and read-only source media remain protected. The [Access cutover procedure](../../engineering/plans/access-architecture-2026-09-08/execution/cutover.md) covers fresh identity state, native re-pairing, and protection of existing Personal Space directories.

## Server folder browsing

Choosing library folders is an administrator action: the Engine's server-folder actions accept only an administrator or the first-run setup session (revoked when setup completes). They browse every ready drive on Windows, or `/` on Linux (inside a container, whatever the container can see), plus any configured storage locations. Listing returns folder names and one "already has files" flag, never file contents. Tuvima's own configuration, key, log, backup and data folders, operating-system folders, and `.data` folders cannot be chosen; a whole drive can be indexed read-only but not managed; and a folder inside a configured read-only storage location stays read-only however it was reached. Managed folders still pass a real write test.
