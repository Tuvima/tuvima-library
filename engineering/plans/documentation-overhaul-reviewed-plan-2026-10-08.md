Guides, Develop, and Reference organize those paths. A first-time reader goes from the landing page to installation; a plugin author goes directly to development guidance. **Acceptance:** all four paths work on a phone and desktop, keyboard navigation is usable, and search finds representative pages. Maps to **WP1, WP3, WP5, WP8**.

2. **Install using instructions that match what is actually available.** Docker comes first, with persistent storage explained and a link to the complete maintained configuration. Windows is presented according to verified release availability and limitations; a release workflow alone does not imply a downloadable, tested installer. Source installation remains available to contributors. **Acceptance:** readers see the correct Dashboard address, keep data through container replacement, and never reach an advertised installer download that does not exist. Setup timing distinguishes downloading images and models from entering settings. Maps to **WP1, WP4, WP6, WP8**.

3. **Understand daily tasks without implementation jargon.** Guides explain Home, For Me, Read, Watch, Listen, View, Collections, Search, details, playback, editing, review, and administration. For example, a reader learns the difference between My List and Favorites, or follows a wrong match into the editor. Required commands, paths, permissions, and warnings stay beside the relevant task; optional internals sit in technical details or linked reference pages. **Acceptance:** the instructions match current behavior, partial features are clearly identified, and needed technical facts are preserved. Maps to **WP2, WP4, WP5, WP8**.

4. **Keep existing bookmarks useful.** Existing guide links retain their destination where possible. Renamed pages lead to the correct replacement, including important heading links. Unknown addresses show a useful recovery page with working navigation. **Acceptance:** the old route inventory resolves to meaningful content under `/tuvima_library/`, with no false successes caused by a generic 404 page returning HTTP 200. Maps to **WP1, WP3, WP8**.

5. **Give maintainers clearer, trustworthy documentation.** The README becomes a product entry point. Contributor guidance and the private security-reporting instructions agree with their site counterparts. Active engineering plans and necessary evidence remain available outside the published site. Superseded material is removed only from a reviewed inventory. **Acceptance:** each retained authority and its required dependencies still resolve; private reporting is usable before it is advertised; agents can regenerate their context from Markdown and MDX. Maps to **WP2, WP3, WP6, WP7, WP8**.

6. **Read complete pages without outdated screenshots.** The README, landing page and guides use the existing logo, clear text, navigation and useful diagrams where applicable. Remove screenshot heroes, strips, galleries, captions and full-size links, including the README's screenshot-only showcase. Do not leave empty frames or coming-soon image placeholders. Better screenshots can be added in a later content update. **Acceptance:** no existing screenshot files ship, no live page or social metadata references them, and both desktop and phone layouts read naturally without them. Maps to **WP2, WP3, WP5, WP6, WP7, WP8**.

The application, media files, databases, permissions, playback, providers, installer, and Docker image are unchanged by this documentation project. Translation, versioned docs, runtime fixes, release engineering, and cleanup of `tools/reports/` stay outside scope. ## Technical approach and scope rules

**Content and route contract.** `docs/` remains the canonical source. WP1 chooses either a working external loader or a generated, ignored staging tree for Starlight. The staging alternative must preserve source edit links, explicit original-source git dates, relative assets, slugs, MDX imports and schema validation. Do not rely on symlinks or generated files having meaningful git history. If neither approach passes, retain MkDocs and present the precise remaining incompatibility before changing source layout.

Build a durable source manifest covering old path, old URL, relevant fragments, destination path, destination URL, audience, final status, owner and action. Load only the manifest's intended publication set; engineering candidates can remain on disk pending cleanup without becoming search results or failing the published-page schema. Keep source-relative Markdown links when a proven compatible transformer works; otherwise use a tested base-aware strategy and record the GitHub-reading tradeoff. A small scoped transform is preferable to a large custom compatibility framework. No unresolved link strategy may be pushed into the writing teams.

**Dependencies.** WP1 resolves exact compatible versions of Astro, Starlight, checks/types tooling and selected plugins against Node 24, their peer requirements and licenses. Latest versions individually are not a compatibility proof. Omit `starlight-image-zoom` for this delivery because screenshots are deferred. Treat sidebar topics as an optional enhancement: first prove whether built-in grouping/navigation meets the experience. Use extensions only when they pass compatibility, license, accessibility and same-origin checks. Keep local search, strict internal links and anchor validation as required outcomes. Record licenses for transitive shipped assets, Pagefind and fonts as well as direct packages; retain font license files, not just package metadata.

**Schema and writing.** Enforce the attachment's required title, description, audience, category and product area. Require meaningful nonempty descriptions and explicit decisions for migrated statuses; do not silently promote planned content to current. Freeze reusable Markdown/MDX examples before writers start. Components must not force every otherwise simple page into MDX. Keep installation prerequisites, essential paths, commands, security information and troubleshooting steps visible where readers need them. Readability scores guide editing and exclude code/tables/navigation; they do not override correctness.

**Public compatibility.** Preserve the docs root and the bytes and paths of `docs/reference/approved-plugins.json` and `docs/reference/wikidata-property-map.md`. The protected Markdown page currently uses `summary`; supply its normalized `description` through an explicit build-time metadata adapter or staged-copy transformation and apply the same strict schema to that result. This is a named source exception, not permission to silently supply missing metadata for other pages. Audit references from protected runtime/test/config files before approving moves; adapt the documentation layout instead of editing those consumers. Retain old asset URLs where known public consumers need them. For removed engineering pages, explicitly classify each old public route as a meaningful canonical replacement or intentional retirement; do not claim every retired working-note bookmark survives. Preserve important old heading IDs or provide documented alternatives.

**Cleanup.** Generate the inventory from tracked files, with sizes, purpose, current authority, completion evidence, references and source hashes. Scan tracked Markdown, MDX, HTML, scripts, configuration and code, plus separately identify local generated references. Avoid sweeping ignored logs into authority decisions. Retain unfinished work even if it has no inbound link. Preserve files required by retained reports, scripts and previews; the attachment's JSON rule requiring both a report link and a script consumer is too restrictive. Moving files does not reclaim Git history, so report working-tree reductions rather than repository-history savings. Do not rewrite Git history.

**Screenshot removal.** WP2 inventories the 15 currently tracked files under `assets/screenshots/` and any other documentation screenshot copies, generated derivatives or references. WP7 removes those files; WP5/WP6 and the integration owner remove their page references in the same integrated change. Search Markdown, MDX, HTML, CSS, configuration and social metadata. This replaces D5's `git mv` and D9's screenshot sections; do not copy the old files into `docs/assets/`, `website/` or `engineering/`. Keep logos, icons, fonts and non-screenshot diagrams/design assets. Old screenshot URLs are intentional retirements, exempt from asset-URL preservation; active references must still be removed. Historical inventory records may name deleted files. Leave Git history intact and retain the existing out-of-scope boundary for `tools/reports/` QA output. New visual QA captures remain local under `.tmp/`; these are verification evidence, not replacement documentation screenshots.

No deletion or engineering move happens in this review. During implementation, the cleanup manifest is the concrete product-owner checkpoint retained from the proposal for other cleanup: approval applies to its exact listed changes. The requested documentation screenshot removal is already authorized and is recorded as such in the manifest, without another screenshot approval request. Unaffected platform and writing preparation can continue while other cleanup decisions are pending. Keep the approved manifest under `engineering/` after execution rather than deleting it.

**Workflow.** Use isolated docs verification without starting the Engine or Dashboard. If implementation needs application development/build verification, first stop only the repository's Engine/Dashboard processes as required by AGENTS.md. Preserve existing wrapper parameters, including `serve-docs.ps1 -Address` and `-InstallDependencies`, with reliable propagation of native npm exit codes. Make the build wrapper run the same check-and-build sequence as CI. Run generation from a resolved repository root on Windows and Linux.

In CI, build and structural checks block all relevant events. External link failures are advisory on PRs, blocking on the scheduled audit; document their behavior on main separately and avoid a transient remote failure gating deployment unless deliberately chosen. Treat 429 as rate-limited/unknown after bounded retries, never verified availability. Limit allowlists to exact instructional localhost/example URLs or justified remote exceptions. Separate workflow/ref build concurrency from deployment serialization so an unrelated PR cannot cancel a main deployment. Restrict write/id-token permissions to jobs that need them and keep scheduled runs from deploying. Do not change `ci.yml`, `docker-publish.yml`, `release.yml` or application files for this migration.

## Acceptance and release sequence

1. **Baseline and spike:** record repository status/commit, previous docs output and route inventory; demonstrate the chosen loader/staging and base behavior with real content. No package compatibility or Windows release claim is considered verified merely because it appears in the attachment.
2. **Build correctness:** clean `npm ci`, `astro check`, site build and PowerShell wrappers succeed. Negative fixtures prove failure for missing required metadata, duplicate routes, broken internal pages and anchors, missing local assets and wrong base paths. Remove injected failures and rerun. Retain regression checks, not a disposable one-off link script only.
3. **Content and authority:** all publication candidates have a sidebar location or an explicit exception such as landing/404; target-state and intentionally internal material are classified. All high-risk installation, persistence, access, recovery, privacy and security-reporting claims are traced to evidence. Additionally sample ordinary feature claims. Check status pages against each other rather than trusting either as automatically correct.
4. **Compatibility:** verify the entire old-route manifest, important fragments and README links against the built site mounted at `/tuvima_library/`. Check destination page identity, redirect refresh/canonical target, no loops and preserved fragment behavior. A 200 response alone is insufficient. Test a genuinely missing nested URL through the intended Pages 404 behavior, not only a direct visit to `/404/`.
5. **Assets and privacy:** verify existing documentation screenshots and derivatives are absent from tracked deliverables and built output, and active image links, captions, galleries and social metadata no longer reference them. There must be no blank image frames or screenshot placeholders. Check fonts/licenses, retained brand assets and logo contrast in both themes. Capture network behavior while loading pages and searching; same-origin applies to site resources, not intentional outbound navigation. Image-zoom checks are removed from this delivery.
6. **Visual and interaction:** inspect the attachment's seven pages at 1920×1080, 1440×900, 768×1024 and 390×844 in both themes, plus the screenshot-free README in GitHub light/dark rendering. Check keyboard access, focus, heading order, sidebar switching, theme persistence, search, tables and long code blocks. Avoid page-level horizontal scroll while allowing deliberate code/table scrolling. Require Lighthouse accessibility at least 95 for landing and one guide, plus manual checks; scores alone do not prove accessibility. Keep captures in `.tmp/docs-review/`.
7. **Repository safety:** protected file hashes/paths remain unchanged; there are no application changes or committed review captures. Validate retained engineering links and relative design assets. Run context generation twice and compare semantic contents, allowing documented timestamps; verify MDX landing and descriptions. Include the protected Wikidata page as a fixture: its original bytes remain unchanged while both the built page and generated context expose its normalized description/status. Scope stale-path checks to current consumers, with explicit exceptions for the retained historical manifest and review records.
8. **Commands:** run required .NET restore/build/test once on the integrated candidate when implementing, retaining the repository's native-asset rules and local Tuvima.Wikidata feed. Run format/dependency/docs checks appropriate to changed files. Exercise documented Docker/installer commands only in suitable disposable environments; unavailable Docker, Windows, credentials or feeds are recorded as unverified gates, never reported as passes.
