# Vault surface inventory

For WP17 (the full leak sweep). Rule (Videos spec D17): for anyone without an unlocked NSFW session, a Vault item is absent. Every action that lists, searches, counts, streams, serves artwork or thumbnails, reports activity or emits a webhook answers exactly as it would for an item that does not exist: HTTP 404, never 403, same body.

Who is "unlocked": a human on their own Dashboard device session whose profile is eligible (not Kids, no content limit), whose mode allows it (PIN entered, or Allowed), and whose idle limit has not run out. Service apps, paired apps (Android, Apple, Roku, TV web), cast, anonymous callers and other device sessions are never unlocked. Vault membership is a library fact: the item's `media_assets.library_id` is in `vault_libraries`.

Status: **Covered** = gated in the Engine with a named test. **Open** = known gap, owner noted; not a release blocker for WP9 but WP17 must close or consciously accept it.

## Hard gates (listed by the WP9 security review; not done, each must be closed before the owning packet merges)

These are not "decide later" items. The packet named must close them, with a test, before it can be approved.

1. **Realtime events to administrators (WP11, WP12, WP17). Closed for the Engine side by WP13.** `IntercomAudience` now routes every event that can name a Vault file or path: review, metadata-harvest and ingestion events by the asset or work id they carry, and the ingestion, `MediaRemoved`, `FolderHealthChanged`, `WatchFolderActive` and `InitialSweepStarted` events by the path they carry against the Vault libraries' source folders (`VaultPathClassifier`). Only an unlocked session with the Watch feature receives a Vault one. `IntercomAudienceVaultEventsTests` lists every constant in `SignalREvents` by reflection and fails for any that is neither classified nor in the `VaultFreeEvents` list with a stated reason; a theory then proves each classified event is refused to an administrator until the session is unlocked. Still open: `IngestionQueueProgress`, `MediaOperationChanged` and `CapabilityStateChanged` are listed as counts-only; a Vault file still counts in the ingestion queue totals (see open item 1 below), and `VaultPathClassifier` reads Vault folders from `libraries.json`, so WP11/12 must keep that the place Vault folders are recorded or point the classifier at the new one.
2. **Unfiltered read services (WP11, WP12, WP17). Playback and history readers closed by WP13.** Now filtered with `VaultSql` and proven by a seeded Vault item in `VaultPlaybackIsolationTests`: `TasteProfileRepository` (taste signals), `UserStateRepository.GetRecentAuthorizedAsync` (Continue Watching, recent progress), `ViewerProgressRepository.GetStartedWorksAsync` (spoiler rule), `ProfileOverviewReadService` (items, recently added, library counts) and `JourneyReadService` (when it is not given an authorized list). Playback telemetry, device state and `system_activity` entries about a Vault file are never written, and `application_events` (the only list webhooks and plugins read) already refuses them by trigger. Still open: `CollectionBrowse`, `CollectionCatalog`, `IngestionPresentation`, `WorkDetail`, `PersonalStatusRepository` (scoped by the authorized asset list, needed for in-Vault watched status), `SearchIndexRepository` (including search suggestions), `IngestionQueueProgressRepository` and `MetadataClaimHistoryReadService`; the Local AI batch runners (`VibeBatchRunner`, `DescriptionIntelligenceRunner`, `SeriesAlignmentRunner`, `SmartLabeler`) still read Vault works' metadata and need an owner decision (ingestion-side).
3. **Keepalive on use for the idle timer (WP10, WP12, WP17). Closed for playback by WP13.** Every Vault response the Engine authorizes for an unlocked session (stream ranges, heartbeat, covers, manifest) restarts the idle timer through `CatalogueResourceAuthorizationService.MarkVaultResponsePrivateAsync` and `NsfwIdleKeeper` (throttled to one write per 15 seconds per session), and the Dashboard video player calls keepalive while a Vault video plays (`VaultPrivacy.ShouldKeepAwake`). Tests: `Vault_PlayingAVaultFile_KeepsTheUnlockedSessionAwake_SoTheIdleLockNeverInterruptsIt`, `Vault_UsingAnOrdinaryFile_DoesNotKeepNsfwModeAwake`, `Vault_ASessionThatHasAlreadyLocked_IsNotWokenByAskingForAVaultFile_AndGetsNotFound`, `Vault_NsfwModeBelongsToOneDeviceSession_AnotherSessionOfTheSameProfileStaysLocked`, `VaultPlaybackPrivacyTests.OnlyAPlayingVaultVideo_KeepsNsfwModeAwake`. Browsing and searching inside the Vault now also restart it from the Engine side (WP14: the browsing gate calls `NsfwIdleKeeper`; not yet covered by a dedicated test, only by the Dashboard watcher test `RealUse_RestartsTheIdleTimer_Throttled_AndALockedAnswerLocksTheDashboard`). Still open: the HLS segment path is covered only by the player timer plus stream-request keepalive.
4. **`/api/v1/nsfw/*` request bodies are never logged (WP12, WP17). Closed by WP13 as a code scan plus the existing service log test.** `NsfwRequestBodyLoggingGuardrailTests` fails if the Engine adds request-body logging machinery (`AddHttpLogging`, `UseSerilogRequestLogging`, `EnableBuffering`), reads `Request.Body` outside the plugin gateway, lets `VaultEndpoints` log anything, or sets a framework request logger below Warning in any shipped settings file; `NoResponseShape_CarriesAPin_AndNoLogLineEverContainsOne` proves the PIN-handling service never logs one. Not done: an end-to-end test that sends a PIN through a running server and scans every sink; the scan stands in for it because a running Engine is not allowed in cloud builds.
1. **Realtime events to administrators (WP11, WP12, WP17).** _Status after WP12: the ingestion started/hashed/completed/failed/item-progress events are suppressed at the source for Vault paths; `MediaOperationChanged`, `CapabilityStateChanged`, `PersonEnriched`, `FolderHealthChanged` and the every-event classification test are still open._ `src/MediaEngine.Api/Realtime/IntercomAudience.cs` classifies a few events by asset or entity id, but the ingestion and operations events (`Ingestion*`, `MediaOperationChanged`, `CapabilityStateChanged`, `PersonEnriched`, `FolderHealthChanged` and the like) carry file names or paths and go to every administrator. Each must be classified by library (so only an unlocked session receives a Vault one) or suppressed at the source for Vault files. Needs a per-event test that lists every event name in `SignalREvents` and fails for any that is neither classified nor proven free of Vault content.
2. **Unfiltered read services (WP11, WP12, WP17).** _Status after WP12: not done._ These read services do not know who is asking and do not exclude Vault items: `CollectionBrowse`, `CollectionCatalog`, `ProfileOverview`, `IngestionPresentation`, `WorkDetail`, `TasteProfileRepository`, `PersonalStatusRepository`, `SearchIndexRepository` (including search suggestions), `IngestionQueueProgressRepository`, `MetadataClaimHistoryReadService` and `JourneyReadService`. Each must either use the authorized projection / `VaultSql` filter or be proven unreachable with Vault ids, with a test that seeds a Vault item and asserts it is absent (404-equivalent) for a locked caller.
3. **Keepalive on use for the idle timer (WP10, WP12, WP17).** _Status after WP12: not done; the Identify and activity routes do not restart the idle timer yet._ The idle lock restarts only on `POST /api/v1/nsfw/keepalive`. Real use of the Vault (browsing, searching, playing) must restart it from the Engine side or the Dashboard must call keepalive on every such action; playback must also keep it alive for as long as it plays (D33: idle lock never interrupts playback). Needs a test for each path.
4. **`/api/v1/nsfw/*` request bodies are never logged (WP12, WP17).** _Status after WP12: the Engine has no request-body logging at all and `VaultLoggingGuardrailTests` fails if any is added; a test that sends a PIN through each route and scans every log sink is still to do (WP17)._ The NSFW PIN, the profile PIN and the administrator PIN travel in these bodies. Check that no request logging, exception middleware, problem-details writer, diagnostics or trace sink records them, with a test that sends a PIN through each route and scans every log sink.

## Open items for WP17

1. Ingestion queue progress counts: `media_operations` has no library, so a Vault file's progress can show in an administrator's counts.
2. Read services not yet viewer-aware and not filtered: `CollectionBrowse`, `CollectionCatalog`, `CollectionMediaLookup`, `LibraryCuration`, `ArtworkLibrary`, `ProfileOverview`, `IngestionPresentation`. They are administrator or settings screens; they must hide the Vault even when unlocked until WP10/12 add viewer-aware versions.
3. Canonical artwork library routes: Vault artwork is meant to live only in `vault_artwork`; ingestion (WP11/12) must never write Vault artwork to the shared artwork tables.
4. `system_activity` entries with an entity id of a Vault file or work are now never stored (WP13). Entries with no entity id that name a Vault file in their detail text are not blocked; decide whether the Engine log view must redact them.
5. Shared records: a Vault work must never merge with an ordinary work or join a shared Series, Person or Tag. The data structure keeps Vault names in separate tables, but ingestion non-linkage is not trigger-enforced.
6. Library creation writes the `vault_libraries` row; adding a folder (`POST /api/v1/vault/libraries/{id}/folders`, unlocked administrator in person, own profile PIN, 404 otherwise) now creates the Vault's `libraries.json` entry (named "Vault", Videos, catalogue presentation, as-is read-only folders) and the folder in it, so the watcher scans it as Vault and `VaultPathClassifier` sees it. Done (folder-attachment packet): the library settings routes (`GET`/`PUT /settings/libraries`, `POST /libraries/mutations`) leave Vault libraries out, keep them on save and refuse to edit one; the one-library-per-type rule ignores them. Still open: other readers of `libraries.json` that list libraries or names to administrators (`AccountEndpoints` library names and grants, `GET /setup` libraries, `IngestionEndpoints`, `ReviewQueueReadService`, `ServerFolderBrowserService` messages such as "already configured for Vault" when a normal folder overlaps a Vault folder); and the folder-adding message for an overlap names the other library.
7. Telemetry exclusion, the Needs Review list queries, library overview and collection search filters have code coverage only; each needs a dedicated test.
9. WP14 left open: the browsing gate's keepalive has no dedicated test; the Dashboard's `/engine-image` proxy forwarding the person's session to the Vault artwork route is checked only locally; performer and studio artwork have no source yet (the tiles fall back to initials or the studio name); only the one still saved at ingestion exists per scene, so hover previews have nothing extra to cycle until more stills are saved; no "last played" sort (watching a Vault file is never recorded); images and galleries are WP16; `IVaultFolderAttachment` is now the real `EngineVaultFolderAttachment` (folder-attachment packet).
8. Dashboard (WP10): idle lock and profile-switch lock are enforced by the Engine; the Dashboard must call keepalive and lock.
