# Slow pages from the 2026-10-21 local check (B17, B29, B31)

October 21, 2026. Bugs from the local check on SHY-DESKTOP (`engineering/validation/batch.md`, group 2 "Slow pages"). Measured on the generated libraries the performance tests use (`LibraryListFixture`: 4,000 and 8,000 works; a real library has more claims per item, so real times are higher). Each number is the median of 5 warm runs; "work" is thousands of SQLite instructions, which does not change from run to run. Re-run with:

```bash
TUVIMA_RUN_MEASUREMENTS=1 dotnet test tests/MediaEngine.Performance.Tests --filter "Category=Measurement"
```

The measurements are skipped unless that variable is set, because together they take about 10 minutes. The budget guardrails next to them run on every build. The tables land in `.tmp/b17-library-summary-measure.md`, `.tmp/b29-detail-measure.md` and `.tmp/b31-people-measure.md`.

## B17: library summary tiles (Settings, Library and Ingestion)

**Cause.** The tiles waited for two Engine reads together:

1. **The library counts read built the whole item projection three times**, each time with every display field (titles, years, authors, genres, directors). The year look-up alone was 134 KB of a 216 KB statement. The counts read none of those fields.
2. **The full readiness report.** It scans the whole data store (integrity and foreign-key checks) and runs a write probe, which queues behind ingestion's writes. The summary only shows the two folder checks.

**Change.**

- The counts now come from one pass over a counts-only form of the projection. The display fields become empty there; every other caller gets the same SQL as before. A test checks the counts match the full projection.
- The summary asks only for the storage checks (`/system/readiness?category=storage`).
- The tiles draw as soon as the counts arrive. Storage problems fill in afterwards.

| Read | 4,000 works before | 4,000 works after | 8,000 works before | 8,000 works after |
|---|---|---|---|---|
| Library counts | 1,758 ms (28,938 work) | 229 ms (6,840) | 3,648 ms (58,058) | 487 ms (13,679) |
| Readiness the tiles waited for, idle | 57 ms | 0.4 ms | 88 ms | 0.3 ms |
| Readiness while ingestion holds a 2 s write | 2,003 ms | 0 ms | 2,003 ms | 0 ms |

Guardrails: `LibraryOverviewGuardrailTests` (work budget of 10,000 at 4,000 works, counts equal to the full projection), `StartupReadinessServiceTests`, and the Dashboard test `LibrarySummary_ShowsItsTilesWithoutWaitingForTheStorageChecks_AndAsksOnlyForTheStorageChecks`.

## B29: details overlay opens slowly, close X against the scroll bar

**Causes** (Engine time to compose one page):

1. **Movie, episode and TV show pages worked out every file's credits to list one title's actors.** They filtered the whole-library credit view by work. This was 98% of their composition.
2. **Show, album and series pages sent every visible file and work as separate values** to two look-ups: personal status (0.3 s at 4,000 works, 1.2 s at 8,000) and display ids (0.4 s and 0.8 s). The data store work was small; binding thousands of values was the cost.

**Change.**

- The actor list now uses the shared per-file credit block (`PersonCreditSql.ScopedCreditsCte`) for the title's own files. It returns the same rows as the view.
- Both look-ups take their ids as one list (`json_each`).
- The id-list guardrail now also catches `allowedAssets`.
- The close button sits 1.5rem in from the window edge (0.75rem on the phone sheet), so it no longer touches the scroll bar.

| Page | 4,000 works before | 4,000 works after | 8,000 works before | 8,000 works after |
|---|---|---|---|---|
| Movie | 1,141 ms | 288 ms | 1,965 ms | 430 ms |
| TV episode | 1,121 ms | 405 ms | 2,171 ms | 534 ms |
| TV show | 2,842 ms | 1,632 ms | 6,259 ms | 2,990 ms |
| Music album | 2,201 ms | 1,681 ms | 5,204 ms | 3,297 ms |
| Book series | 2,071 ms | 1,539 ms | 4,942 ms | 2,972 ms |
| Book in a series | 317 ms | 315 ms | 504 ms | 506 ms |
| Audiobook | 349 ms | 388 ms | 577 ms | 586 ms |
| Person | 611 ms | 649 ms | 879 ms | 749 ms |

Book, audiobook and person rows are unchanged within noise.

Guardrail: `DetailOpenMeasurementTests.MovieEpisodeAndShowPages_ComposeWithinBudgetAtFourThousandWorks`. The budget is 5,000 work; before the change, a movie took 51,220.

**What is left.** Show, album and series pages first read the whole library's visible works: 1.3 s at 4,000 works and 2.6 s at 8,000. The Engine keeps that list for 30 seconds, so only the first open after a pause pays it. Narrowing it to the page's own works changes which works the page is allowed to see, so it is an access-rule change. It is proposed as a follow-up, not made here. The "load the essentials first" idea (hero first, the rest after) is not built. With the composition now 0.2 to 0.4 s, that read is the remaining wait, and a two-step page would not remove it.

## B31: People faces about 200 KB each

The picture half (a 96 px face copy, sized requests and browser caching) belongs to the Locked spec [Right-sized pictures on every screen](../specs/right-sized-pictures.md), built in its own session. The People list already lazy-loads faces.

**The data half.** The People section's reads, measured one by one:

| Read | 4,000 works | 8,000 works |
|---|---|---|
| Collection catalog | 6,409 ms | 23,576 ms |
| People list | 4,128 ms | 8,835 ms |
| Role counts | 2,842 ms | 6,377 ms |
| Presence counts, list cached | 1,922 ms | 4,493 ms |
| Content groups | 188 ms | 419 ms |

**Causes.**

1. The page waited for all four first reads before showing any section. People therefore waited for the collection catalog, which People does not show. The catalog grows faster than the library: about 3.7 times when the library doubles.
2. The list, the role counts and the presence counts each read every credit in the library through the credit view: about 82,000 work each at 4,000 works.
3. The list, role counts and presence reads each read the whole library's visible works. That list is cached for 30 seconds, but two cold requests both build it.

**Change.** The open section now shows as soon as its own reads arrive. The other sections fill in behind it, and a section chosen early says "Loading" until its data is in. A Dashboard test holds the catalog read open and checks that People still shows.

**Time until the People list shows**, worked out from the measured reads (the list and role counts start together, then presence):

| | 4,000 works | 8,000 works |
|---|---|---|
| Before (catalog, then presence) | about 8.3 s | about 28.1 s |
| After (People reads only) | about 6.0 s | about 13.3 s |

Collections, Shelves and Overview no longer wait for the people reads either.

**What is left.** The People reads themselves still read every credit (cause 2) and the whole visible-works list (cause 3). Moving them to the per-file credit block is item T3 of the [library read speed follow-ups](../handoffs/2026-10-21-library-read-speed-follow-ups.md), which needs a plan approved first. Within T3, the visibility check on a page of people could look at those people's own credits instead of building every visible person. The collection catalog's growth needs its own look. Three playback-state reads also send library-sized id lists one value each: audiobook bookmarks, listen history and saved progress (`AudiobookBookmarkRepository`, `AudiobookListenHistoryRepository`, `UserStateRepository`, `IN @allowedAssets`). That is T2's subject, and they are left for it.
