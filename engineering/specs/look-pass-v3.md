## 1. Goal

The Dashboard reads as one product on every screen: the same five dark surfaces with the same meaning everywhere, purple only where something is chosen or primary, one UI typeface with four weights that never shout, Settings that reads as one calm page instead of a stack of boxes beside a differently coloured menu, and tooltips that appear only when they tell you something the screen does not.

## 2. What is actually wrong today (findings)

### 2a. Colour: the right palette, applied to about half the app

The near-black ladder from Look v2 (page `#101115`, nav `#14151A`, cards `#1A1B21`, hover `#272830`, menus `#2F3039`) is in the token file and used by Home, the details pages and the editor. Four colour families were never moved onto it, and they are exactly the screens Shy noticed:

1. **Every dropdown and menu is still purple** (verified, bug 13, decided A). The shared menu tokens are a dark violet surface (`rgba(18,11,42)`), a 65 % purple border, purple hover and selected tints and lavender icons. A second family, the "secondary action" tokens, paints button fills in purple too. Six places read these tokens, so one change fixes all menus, the season and episode dropdown, the hero thumbs pop-up and every "..." menu.
2. **The whole Settings area, and the Watch, Listen, Read, View and Collections section pages, sit on their own navy** (verified). The section shell that frames these pages paints its own background: a navy gradient (`#070b14` to `#05070c`) with a purple radial glow, and the left rail (the Settings menu) is `rgba(7,12,23,.86)` on top of that. Those are the pre-Look v2 colours. This is why the Settings sidebar is "a different colour": the page content is near-black `#101115`, the rail beside it is navy, and the page background behind both is a third dark. The same file carries 14 hand-typed purple values for hover and selected rows.
3. **The players keep a navy family of their own** (`--player-bg #0F131E`, `--player-surface #121623`, pop-out surface `rgba(18,22,35)`). Look v2 packet A13 planned to fold these into the shared tokens; the unified player plan now owns the player and should consume the shared tokens rather than keep this family.
4. **Hand-typed colours everywhere else.** 651 hex colours in component styles and 111 in the global sheet, 218 distinct hex values across the Dashboard. The worst files are the details pages (three files with 19 to 24 each), the artwork workspace, the View pages, the account menu (13) and the media tile (11). Each of these is a place a future palette change will miss again.

The rule that is missing is not a palette but **roles**: which surface is for what, and which colours may appear where. Section 4 states it; a guardrail keeps it.

### 2b. Settings reads as boxes, not as a page

Verified from the Settings frame, the shared card and the pages:

- Every Settings tab is a **stack of bordered cards** (`AppCard`): each has a 1 px border, its own fill, 20 px padding, a 28 px icon and an 18 px bold title. Pages hold three to five cards per tab (Notifications 5, Managed access 5, Advanced network 5, File handling 4). Tables inside add a second set of borders. On a near-black page every card is an island, which is the "bunch of blocks" effect.
- The **left rail is a different dark** (finding 2a.2) with purple-tinted hover and selected rows, and the rail is 256 px with a 15 px inset and its own scrollbar colour.
- The **content column is capped at 1180 px and centred**, so on a wide screen the rail sits at the far left and the cards float in the middle with empty space either side.
- Titles inside Settings use **three bold sizes** (page title 24/600, card title 18/700, section-card title 18/700 plus an uppercase eyebrow at 13/700 with 0.11 em spacing) and tables add 700-weight headers. Weight 700 is used 238 times across the Dashboard against 181 of 600 and only 39 of 500: bold is the most common weight in the app, so nothing stands out.

Apple's System Settings, Plex and Jellyfin all do the same thing here: one page background, groups of rows with hairline dividers, a short group heading, the control at the right end of its row, and a card only for a thing that is an object (a backup destination, a connected device) or a danger zone.

### 2c. Fonts: no UI font is shipped, so the app looks different on every device

Verified from the font rules:

- **Body text is the device's font** ("Segoe UI Variable", then system-ui). On Windows that is Segoe; on a Mac it is San Francisco; on Android it is Roboto; on a TV or a Linux box it is whatever exists. The Dashboard therefore never looks the same twice, and Segoe at 14 px with heavy weights is what Shy is looking at on SHY-DESKTOP.
- **Tuvima Sans** (a Montserrat derivative, 216 KB woff2) is used only for the wordmark and the top navigation, by Shy's earlier decision. **Montserrat** (689 KB, TTF, not compressed) is shipped only as its fallback, which is a large download for a font nobody sees unless Tuvima Sans fails. **Merriweather** (Regular and Bold, TTF) is the reader's book face. **JetBrains Mono** (270 KB TTF) is for paths and codes.
- Seven places hand-type a Georgia serif stack instead of the reader token; two use a `--font-display` token that is never defined, so they silently fall back.
- **Sizes:** 225 distinct `font-size` declarations remain in component styles after Look v2 (most are now tokens, but 306 uses of 12 px and 157 of 13 px mean a lot of the app is small text). **Weights:** 700 is the most used. **Labels:** 18 uppercase labels with 12 different letter-spacing values. The root font size is 14 px while menus are 16 px.
- The wordmark lost its uppercase in the Look v2 sentence-case sweep (bug 9, verified) because the brand mark was not exempted.

### 2d. Tooltips appear everywhere, repeat labels and get stuck

Verified from the tooltip scripts and a count of sources:

- **304 sources**: 133 `title="…"` attributes (a ratchet allows up to 186), 124 `Tooltip=` settings on shared buttons and 47 `AppTooltip` wrappers. A global script turns every `title` into the app's tooltip after 150 ms, so anything that ever had a browser hint now has a fast, styled one, including menu rows whose tooltip is their own label (bug 17).
- **Nothing hides a tooltip when its control goes away.** The tooltip is a separate element in the page's top layer. Blazor redraws controls constantly (a list refreshes, a button swaps, a dialog opens), and no code notices that the hovered control was replaced, so the bubble stays until the next hover, scroll or Escape (bug 27). There is no maximum display time on a mouse (touch has 1.5 s).
- **The `title` grab repeats after every redraw**: the script removes `title` on first hover, Blazor restores it on the next render, and the grab runs again, which can produce a second bubble or one on the wrong element.
- The look (menu grey, 13 px, no arrow, top layer, inside open dialogs) is right and stays.

### 2e. Other general inconsistencies

- **Icon buttons are styled in four places** (bug 11, verified by the local check): the shared circle in the global sheet, the hero row, the rate control and the purple fill on the rated thumb. The home tile "..." inherits the shared button's outline and is invisible on light covers (bug 30c). There is no "plain icon over artwork" variant.
- **Two names for every token**: 34 `--app-*` aliases and a block of 24 `--tl-*` aliases ("tokens that older styles referenced without a definition") mean a new page can pick either name and both must be kept forever.
- **705 `!important` in the global sheet and 577 in component styles.** Every fix becomes a fight with a stronger rule, which is why styles drift: it is easier to add a new override than to find the old one.
- **The design-system document is out of date** (dated 2026-10-17): it still says "deep navy surfaces", lists the old navy values and Segoe as the interface font. A builder who reads it builds the old look.
- Breakpoints off the 600/840/1180 ladder remain in older styles (27 rules at 720, 30 at 640); the guardrail only covers new CSS.

### 2f. Icons have sizes but no rules for how they sit with text (added 2026-11-07, Shy)

Verified: the icon part takes its size through **twelve different spellings** (`AppControlSize.Compact` 286 times, `AppSize.Small` 188, `"Medium"` 17, `"compact"` 12, `"standard"` 4, `"Provider"` 3 and so on), so two builders asking for "a small icon" get different sizes. Component styles also set icon widths by hand (22 px in ten places, then 24, 20, 48, 27, 26, 18, 16, 15, 12 and 11 px). The icon tile part has three sizes (28, 42, 48 px) but no rule for when an icon sits **above** its text (a tile or card you choose from: Add library's area tiles, the setup area cards, empty states) or **beside** it (a button, a rail row, a list row, a chip). The Add library tiles broke in exactly this gap (local check bug 1: a 28 px icon in a 160 px tile, text to the right instead of underneath, because the shared button forces 18 px icons and a horizontal layout).

### 2g. Windows, sheets, pop-outs and pickers are built 82 different ways (added 2026-11-07, Shy)

Verified: 82 files build something that floats over the page. The shared dialog exists and is used, but nine screens hand-build their own `role="dialog"` (the document viewer, extra viewer, book reader, security sheet, library folders pop-over, search overlay, details overlay, Vault image viewer, profile editor sheet) and two draw a raw `<dialog>`. Widths vary by part: the shared dialog caps at 700 px, the player's tool sheet at 400 px, the small pop-over at 140 px, the search overlay at 1,540 px; corner radii run from 6 px to 18 px; padding from 12 to 24 px; the player's sheets have their own handle, rows and list parts. There is no ladder of window sizes and no rule saying which kind of thing is a window, a sheet, an anchored pop-out or a full-screen viewer.

## 3. Scope

**In scope**
- Colour roles and the surface, border and accent rules, applied to the section shell and rail, menus, players' shared surfaces (tokens only), and a ratchet on hand-typed colours.
- One Settings page model (groups and rows, rail colour, width, headings) and the shared parts that make it.
- One shipped UI typeface, the size and weight ladder, label style, font file hygiene, the wordmark fix.
- Tooltip rules, behaviour fixes, migration of the 133 `title` hints and the guardrails.
- One icon button with three variants, consumed by hero, tiles, rate control and the players.
- Icon rules: one size ladder, icon-above-text tiles and icon-beside-text rows, as shared parts.
- Window rules: one ladder of window sizes and four kinds of floating surface, used by every dialog, sheet, pop-out, picker and viewer.
- Cascade cleanup (aliases, `!important` ratchet) and the design-system document rewrite.
- The design preview page as the single proof page.

**Out of scope**
- Player layout and behaviour (the unified player plan), the editor layout (Editor v5), tiles (One tile design), Libraries and Activity layouts. They consume the tokens and parts below and define none of their own (same rule as the Look v2 ownership map).
- New features, light theme, editing on phones.

## 4. Decisions made

Shy answered every question on 2026-11-07 06:33Z ("agree on all questions"): **1A** Inter everywhere, Tuvima Sans brand only · **2A** Settings as groups of rows, cards for objects only · **3A** rail in navigation grey with a hairline · **4A** tooltips only icon-only, disabled-with-reason, cut-off text · **5A** neutral hover, purple only when selected · **6A** Look v3 wave 1 before the player and editor builds · **7A** choice tiles with a tinted square · **8A** window widths 480 / 640 / 900. Decisions marked (P) below were proposals and are now locked by those answers.

- **D1 (Look v2 D1, stands).** Surfaces: page `#101115`, nav and rail `#14151A`, card `#1A1B21`, hover `#272830`, raised and menu `#2F3039`. Purple `#8852FC` is an accent (text and icons use `#A46FFF`).
- **D2 (Shy, bug 13, A).** Menus and dropdowns are neutral: menu surface `#2F3039`, border `--tl-border-default`, hover a neutral 6 % white wash, selected row the purple soft wash with a purple text or marker, icons `--tl-text-secondary`. No purple border on menus.
- **D3 (P). Colour roles.** Surface tokens are the only backgrounds in the Dashboard; purple appears only as: selected (nav row, tab underline, chip, menu row), primary button, switch on, progress, focus ring, the Like state. Area colours (Watch, Listen, Read, View, Vault) appear only in chips, icon tiles and area labels. Status colours appear only on status. Nothing else is coloured. A guardrail fails a component style that contains a hex or `rgb()` colour outside an allowlist (charts, subtitle swatches, the map, avatars).
- **D4 (P). The section shell and rail use the tokens**: shell background = page, rail = nav `#14151A`, a 1 px `--tl-border-subtle` divider, rail rows 44 px with the neutral hover and the purple soft selected wash. No gradient, no glow. This applies to Settings, Watch, Listen, Read, View and Collections at once because they share the shell.
- **D5 (P). Settings is one page**: page title and one-line description, tab row (Advanced stays amber and last, Settings spec D1), then **groups**: a 16/600 heading, an optional helper line, and **rows** (label and helper on the left, the control on the right, 56 px min height, hairline between rows), on the page background with no card border. A card remains only for an object (a backup destination, a connected device, a tool, a plugin) and for a danger group (outlined red). The content column fills the space beside the rail up to 1180 px and is left-aligned to the rail, not centred.
- **D6 (Shy, 1A). One UI typeface, shipped.** **Inter** (variable, SIL OFL 1.1, AGPL-compatible, one woff2 of about 300 KB for Latin) for every piece of interface text, so the Dashboard looks the same on Windows, Mac, phones and TVs. Tuvima Sans stays for the wordmark and top navigation only (Shy's standing decision). Merriweather stays in the reader; JetBrains Mono for paths. Montserrat's 689 KB TTF goes (Tuvima Sans is self-hosted and never fails to a webfont), and the remaining TTFs become woff2.
- **D7 (P). Type ladder, enforced.** Sizes 12 caption · 13 secondary · 14 body · 16 controls, menus, rows · 20 section and shelf · 24 page title (28 at 1180+) · 32 hero. Weights 400 body · 500 labels, menu rows, chips, buttons · 600 group headings, card and row titles · 700 page and hero titles only. Line heights 1.2 / 1.3 / 1.5. No uppercase labels except the wordmark (brand exemption added to the sentence-case rule); the one overline style, if a page needs one, is 12/600 at 0.06 em. The ratchet tests move from "may only go down" to the ladder values.
- **D8 (P). Tooltip rules.** A tooltip exists only when (a) the control is icon-only, (b) the control is disabled and the tooltip says why, or (c) text is cut off and the tooltip shows it in full. Never on a control with a visible label that says the same, never on list or menu rows. Behaviour: hide when the control leaves the page or is replaced, on any press anywhere, when a menu or dialog opens, after 4 s on a mouse; keep 150 ms show, 0 ms on keyboard focus, long-press on touch. The global `title` script is retired: every hint becomes a `Tooltip` parameter or an `AppTooltip`, and `title=` drops to the four-element allowlist. Guardrails: no `title=` outside the allowlist; no tooltip equal to its control's visible text (a render test over the preview page and a text check over the Razor files).
- **D9 (P). One icon button, three variants**: Outlined (default, on surfaces), Plain (no border, no fill; a soft dark scrim when placed over artwork, used by the tile "..." and hero companions) and Filled (primary and the Like state). Sizes 36 / 44 / 48 with icons 20 / 24 / 24. The hero row, tile menu, rate control and the player dock use it; no local icon-button styles remain.
- **D12 (Shy, local check bug 10, 10b = A). One shared hero button.** Home hero and the details hero use the same `HeroActionRow`: one wide solid **light** (white, dark text) Play / Watch / Resume / Read / Listen button, **56 px** tall with a 20 px label and a 24 px icon, thin progress bar under Resume; companions are the Plain icon-button variant (D9) at 48 px with a short label under them where the row has room (My List, Like, Edit on desktop, More). A folder of videos gets an **Open** companion with a folder icon in the same style, never a text link (10a). This supersedes Look v2's "Play is a plain purple fill" (D1 and A7) as a deliberate override: purple stays for selected and primary states elsewhere; the hero's main action is light so it reads over any artwork. Home tile "..." (bug 30c) is the Plain variant: no outline, a soft dark scrim, visible on any cover.
- **D13 (P). Icons: one ladder, two placements.** Sizes 16 inline and chips · 20 in 36 px controls · 24 in 44 and 48 px controls, menus, rail rows and list rows · 32 in dialog and card icon tiles · 48 in choice tiles · 64 in empty states and the hero of a setup step; the icon part takes only these five names and nothing else sizes an icon. **Above text (a choice tile):** a square tile at least 120 px, the icon 48 px on a soft tinted square (the area colour at 14 % for area tiles, neutral otherwise), the label under it at 14 / 500, an optional second line at 13 / 400 muted, centred, 12 px between icon and label; used by Add library's area and kind tiles, the setup area cards, the "What is this file?" choices and the empty states (64 px, no tinted square). **Beside text (a row or button):** the icon leads, 24 px in rows and 44 px buttons, 20 px in 36 px buttons, 12 px gap, vertically centred on the first line of text, the icon in `--tl-text-secondary` unless the row is selected or carries a tone; used by buttons, rail rows, menu rows, list rows and chips (16 px). Icons never sit to the right of their label except a trailing chevron or a trailing "..." in a row. One part each: `AppChoiceTile` (above) and the existing button, row and chip parts (beside).
- **D14 (P). Windows: four kinds, one ladder.** Everything that floats over the page is one of four kinds, each one shared part: **Window** (centred, scrim behind; sizes S 480 px for a confirmation or a short form, M 640 px for a form or picker such as the provider key window or the folder picker, L 900 px for a workspace such as the editor, the artwork picker or the collection editor; 12 px corners; one anatomy: 20 / 600 title, optional one-line description, close X at 44 px top right, body, footer with Discard or Cancel on the left and the one primary button last; a destructive button is outlined red and sits left of the primary), **Sheet** (the Window on phones: slides from the bottom, 16 px top corners, a handle, the same anatomy; every Window becomes a Sheet under 600 px, no page opts out), **Pop-out** (anchored to its control, no scrim, closes on outside press or Escape; sizes: Menu 272 px with 44 px rows, Panel 400 px for tools such as the player's speed, audio, subtitles and queue, and the library folders pop-over; 8 px corners; the raised surface; on phones a Pop-out becomes a Sheet), and **Viewer** (full screen, black or page surface, for the reader, the photo and document viewers, search and the details overlay; its own close X at 44 px and the same tooltip and menu parts). Hand-built `role="dialog"` and raw `<dialog>` markup are retired; a guardrail allows the four shared parts only. Players, pickers and the editor consume these kinds. **Ownership note (2026-11-07):** Look v3 owns only the window frame (kind, width, corners, title, close, footer). The browser inside the folder picker and the supporting-files picker is one shared browser frame owned by Editor v5 (its D32 and WP8a); Look v3 does not touch its contents, and that browser opens in an M (640) Window, or L (900) if Editor v5 needs the room for filters and groups.
- **D15 (P, Shy 2026-11-07 via Editor v5). Alignment rules, enforced.** (1) **Rows.** Every row (settings row, list row, rail row, toolbar, form row) is one flex line with its label, helper and control vertically centred on one axis; a label never wraps inside a toolbar or button row (it shortens with an ellipsis and shows the full text in a tooltip, D8c); a label may wrap only in a settings or list row, and then the control stays centred on the whole row. Row heights come from a ladder: 44 (menu, rail, toolbar), 56 (settings and list rows), 64 (rows with a picture). (2) **Labels and fields.** A form field's label sits **above** the field (13 / 500, 6 px gap), the same on every width, as the editor already does; helper text sits under the field at 13 px muted. A settings or list row is the other shape: label and helper on the left, the control at the right end, one centre line. The two shapes never mix in one group. A label is never right-aligned and never inside the field. (3) **Buttons.** In a footer or toolbar, buttons sit in one row, right-aligned, Cancel or Discard left of the group and the one primary button last; a destructive button is outlined red and sits left of the primary; a quiet (text) button is leftmost. Buttons in one row share one height and one baseline; an icon-and-word button keeps the icon 20 or 24 px with an 8 px gap. Buttons never stack on desktop and stack full width on phones, primary first. (4) **Text.** Left-aligned everywhere except numbers and durations (right, tabular numerals) and choice tiles (centred). No `text-align: center` on body copy, dialogs or settings. (5) **Crowding.** A toolbar or header row holds one group on the left and one on the right, both on the row's centre line; a right-aligned segmented control or switch on a form row is allowed as long as nothing in the row wraps. When a row needs more than three actions, the rest go into "...". The Match row keeps one row (provider dropdown left, icon-only Search, the Media providers · Wikidata segmented control right); the fix is that its label never wraps inside a cell and the control sits on the row's centre line. (6) **Text never rides on a control (Shy 2026-11-07).** Helper, status, error or result text that belongs to a control ("Saved", "Testing…", "Key is invalid", a count under a field) is never placed above or below the control inside its column. It goes on its own full-width row directly under the row that holds the control, at 13 px, and that row is reserved (it keeps its height, or appears and disappears without changing the control row), so a control in the other column never shifts up or down. The only text allowed inside a control's column is the control's own label on a form field (above it, D15.2). **Enforcement:** `tools/validate-alignment.js` runs on the preview page and on four real screens (Settings Playback, the editor Match tab, a details page, the folder picker) and fails when a label and its control differ in centre line by more than 2 px, when a button row has mixed heights or the primary is not last, when a toolbar label wraps, or when a row height is off the ladder, or when any text sits above or below a control inside the same column (a vertical offset between two controls on one row); a Razor guardrail forbids `text-align: center`, `margin-top` nudges and `vertical-align` on shared row parts outside the allowlist.
- **D16 (Shy 2026-11-07, 06:45Z). This is a unification and cleanup.** Every page, window and part is covered, not only the shared ones: parts, pages, addresses, scripts and styles that nothing uses are deleted (the [cleanup audit](../design/look-pass-v3-cleanup-audit.md) lists them), old naming lists from the component-library migration are retired, and every one of the 42 pages is walked against these rules and recorded with a verdict.
- **D17 (Shy 2026-11-07, 06:55Z). No redirects or address forwarding anywhere.** The app is pre-beta, so nothing has to keep working at an old address. An old or retired address is simply **not found**; no page, part or middleware silently takes the person somewhere else. This extends Settings spec D19 (retired Settings addresses) to the whole Dashboard. Concretely: the Operations shim and its five addresses go; the Libraries tab's forwarding of old `?type=` and `other-` style addresses to the current library address goes, together with its renamed-type map; the four spelled-out View artwork addresses (`/view/artwork/media`, `people`, `universes`, `assets`) are deleted if no in-app link uses them, otherwise they stay as real addresses with their own filter, never as a forward; the Settings and details-tab "not the canonical spelling, so replace the address" logic is removed: a misspelled tab or section is not found, and an unknown tab shows the page's first tab without changing the address. Address replacement that is part of an action stays and is not a redirect: closing the Vault, finishing an action that removed the current item (the details overlay's replace), leaving a deleted profile, switching profiles, and the sign-in and change-password gates (security, not navigation). Every in-app link, notice and docs page points at the current address in the same change, which the existing link test proves. **Guardrail:** a test fails any `@page` address that renders only a forward, any `NavigateTo(..., replace: true)` or `Results.Redirect` outside a named allowlist (Vault exit, details replace, profile switch and delete, culture cookie, password change gate), and any file or method named `Legacy*Address`, `*Redirect*` or `*Alias*` in the Dashboard outside that list.
- **D10 (P). Cascade hygiene.** The `--app-*` and alias blocks retire (one name per token); `!important` becomes a ratchet that only goes down; the design-system document is rewritten from the token file as part of this spec and dated.
- **D11 (P). Proof page.** `/design-system/components` becomes the one page that shows every token and primitive in every state. Visual proof (Mock | Live at 1024 / 1280 / 1440 / phone) is taken against it plus one Settings page, one menu and the Home hero.

Empty, loading and error states are unchanged.

## Plain English summary

The colours Shy chose are right, but only half the app uses them: every menu is still purple, and the Settings area, together with the Watch, Listen, Read and View side menus, still paints its own navy background, which is why the Settings sidebar looks like a different colour. Settings feels like blocks because every setting sits in its own bordered box; the fix is to show settings as groups of rows on one page, the way phones and Plex do, and keep boxes only for real things like a backup destination. The app has no typeface of its own: it borrows whatever font the device has, and it uses bold far too often, so the text looks different on every machine and nothing stands out. Shipping one interface font and a short rule for sizes and weights fixes that for good. Tooltips are everywhere because a script turned every old browser hint into a tooltip, and nothing removes a tooltip when the thing under it changes. The plan limits tooltips to the three cases where they help, makes them disappear reliably, and adds checks so none of this drifts back. Because the app is pre-beta, old addresses are not quietly forwarded to new ones either: they simply stop existing, and a check keeps it that way.
