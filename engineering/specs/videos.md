# Spec: Videos in Watch (downloads, courses and saved channels) and the Vault

> **Status:** Locked · **Version:** 28 · **Last updated:** 2026-10-20 · **Related docs:** [Details overlay and edit mode spec](details-overlay-and-edit-mode.md) · [Product overview](../product/overview.md) · [Presentation rules](../../docs/product/presentation-rules.md) · [Ingestion and readiness spec](ingestion-and-readiness.md) · [Developer tools spec](developer-tools.md) · [Universe spec](universe.md) · [Delete from library spec](delete-from-library.md) · [Privacy and local-first](../../docs/explanation/privacy-local-first.md)

## 1. Goal

People own videos that no movie or TV database knows: a saved YouTube channel, a programming course, a recorded lecture series. Today Tuvima cannot present them. This spec adds a **Videos** shelf to Watch that turns a folder of such videos into a proper series (sections, episodes in order, resume, Up Next), identifies YouTube downloads with a light online lookup, and keeps phone memories where they belong, in View with photos. Adding a folder makes that choice clear.

Approved scope: the Videos packets (V0 to V6) were approved by Shy on 2026-10-13 (Documents plan). This version amends them with Shy's decisions of 2026-10-20 (D1 to D6).

## 2. Scope

**In scope**
- A seventh library type, **Videos**, in Watch, alongside Books, Audiobooks, TV Shows, Movies, Music and Comics.
- An "Add folder" step that separates **Videos (Watch)** from **Photos and personal videos (View)**, with a hint for folders that look like phone footage.
- Folder reading: loose file = standalone video; folder of several = series; sub-folders inside a series = sections; files = episodes, in order.
- Identification without a movie/TV database: a YouTube ID, a `.info.json`, a Kodi `.nfo`, then the cleaned file name. Each item records how it was identified.
- A Watch shelf, series page and standalone page that behave like TV (cover, description, sections, episodes, progress, Resume, Up Next, mark watched) on phone, tablet, desktop and TV.
- Editing in Editing Mode (desktop only): title, description, cover, tags, order, and moving a video between standalone and series.
- Sidecar files: `.info.json`, `.nfo`, `cover/folder/poster` images, `.srt`/`.vtt` subtitles, chapters inside the file; a good still-frame thumbnail.
- A **YouTube metadata provider** built on the new plugin system (an Official plugin).
- Documentation updates (public site and engineering docs) for all of the above.

**Out of scope**
- The Popular Bookmarks plugin itself (placeholder only, D47), community sharing and review (a separate plan, D48), tags on bookmarks, sharing personal bookmarks between profiles other than through packs, and outside lookups for images.
- Phone memories and home videos: they stay in View with photos (galleries, timeline). Nothing about View changes.
- Downloading videos (no YouTube downloading, ever), live TV, auto-translation, subtitle generation.
- Other video sites (Vimeo and so on): v1 reads their `.info.json` and file names only; more sources arrive later as plugins (D5).
- Any adult metadata source other than Stash-box, studios browsing, and Vault on native, TV and cast surfaces (D20 to D22).
- Putting Videos into Universes: a Videos series is a Series, never part of a Universe in v1.
- Moving an item between Watch and View automatically (D6).

## 3. Decisions made

- **D1. Videos live in Watch, as a catalogue type with no movie/TV lookups** (Shy, 2026-10-20). They become real titles, so the existing player, resume, Up Next and show page work unchanged. Reason: Maintenance and Uniformity (one way to watch, one place progress lives).
- **D2. Real videos go to Watch; phone memories go to View** (Shy, 2026-10-20). YouTube downloads, courses and anything needing structure belong in Watch. Videos pulled from a phone as personal memories belong with photos so they get a gallery. Reason: the two need different presentation.
- **D3. Adding a folder asks which one it is** (Shy, 2026-10-20): "Videos (Watch)" or "Photos and personal videos (View)"; with NSFW mode on, a third choice for the adult area (D45) also appears. A folder that looks like phone footage (camera-style names such as IMG_1234 or MOV_0042, a DCIM folder, mostly short clips with camera information) gets a gentle hint suggesting View. The choice is never made silently. Reason: prevent, don't patch.
- **D4. The type is called "Videos"** (Shy, 2026-10-13). A file directly in a Videos folder is a standalone video; a sub-folder holding several videos is a series; sub-folders inside a series are sections; a sub-folder holding one video stays standalone.
- **D5. How a video is identified** (Shy, 2026-10-20), first match wins: (1) a YouTube video ID in the file name (`[abc123XYZ_-]`) or its `.info.json`; (2) a Kodi `.nfo` file; (3) the cleaned file name (number and title). Folder names become series titles. The item stores how it was identified and the series page shows a small "How we identified this" note. YouTube is the only online source in v1; other downloads use their `.info.json` and file names, and more sources come later as plugins.
- **D6. A video in the wrong place is fixed by removing the folder and adding it again under the other choice** (Shy, 2026-10-20). No automatic moving. A clear message explains this.
- **D7. Online lookup (stage 1) for YouTube** (Shy, 2026-10-20): sends only the video ID, fills blank fields only (title, channel, thumbnail; description and upload date need the person's own free YouTube key), and the person's own edits always win. The wording says plainly "this contacts YouTube". There is a switch per Videos library, on by default. Reason: Privacy means not sharing the user's data; sending an ID the app already has is the same kind of lookup the other providers do.
- **D7a. Bundled plugins need no approval step** (Shy, 2026-10-20). The "new plugins start off until approved" rule in the Developer tools spec is for community plugins only. The YouTube plugin ships with the Library as an Official plugin and is on from the start; its building is part of this spec (WP8). The Developer tools spec's wording for Official plugins (D-C) differs; that spec should be revised to match, and this spec does not wait for it.
- **D8. The YouTube lookup is a metadata provider built on the plugin system** (Shy, 2026-10-20): a JSON-defined Official plugin shipped with the Library, appearing in Plugins and Metadata Providers with the standard state card. Any key sits in the secrets store, never in the data store. Reason: Extensibility; this is the first provider outside TMDB/TVDB-style catalogues and proves the model.
- **D9. Documentation is part of the work** (Shy, 2026-10-20): the public site and engineering docs are updated to describe the seventh type, the Watch/View choice, how videos are identified and the YouTube privacy note (WP18).
- **D10. Series order:** number in the file name, otherwise natural sort (2 before 10). Reordering by hand is saved in Tuvima and does not rename files, except in Managed folders where the person chooses "rename files to match".
- **D11. Covers:** the person's own image, then `cover.jpg`/`folder.jpg`/`poster.jpg` in the folder, then the lookup thumbnail, then a good still frame (never a black tile). No hover preview.
- **D12. Tags are global** (Documents plan decision): the same tag list, shown only on things the viewer can see.
- **D13. Editing is desktop-only** through Editing Mode on the item's page, like every other title. No new management screen.
- **D14. Deleting Videos uses the recycle bin** (Shy, 2026-10-20): a deleted video goes to the recycle bin first and leaves the disk only when the bin is emptied, as for View files. The Delete from library spec records this rule for Videos (WP5 carries the hook).
- **D15. Ratings and explicit content** (Shy, 2026-10-20): saved videos have no ratings, so Videos are hidden from content-limited profiles (G to R) until an administrator marks the Videos library "OK for limited profiles"; profiles set to Everything always see them. Any library, series or video can be marked **Explicit** by a person who can edit it; an explicit item is never shown to a content-limited profile whatever the library setting says. Explicit is a plain flag stored on the item.
- **D16. Adult material has its own top-level area, not a corner of Videos** (Shy, 2026-10-20, replacing the earlier flag-inside-Videos design). See D45. The rules D17 to D44 apply to that area.
- **D17. One concept, "Vault".** Marking an item or folder Explicit (D15) makes it Vault. A Vault item is invisible by default to everyone: it never appears in Home, Search, Recently Added, Continue Watching, Recommendations, notifications, the Activity log (not even a count), webhooks, casting or the native and TV apps. A person who cannot see it cannot learn it exists: the Engine answers "not found", not "not allowed" (the same rule as Documents-off profiles).
- **D18. Per-profile access, set by an administrator** (Shy: "a PIN, or invisible for certain profiles, or invisible to everyone until a PIN is entered"): each profile is **Off** (default, invisible forever), **PIN to unlock** (invisible until that profile enters its PIN, then visible until it locks again) or **Allowed** (visible without a PIN; adult profiles only). A content-limited or Kids profile can only be Off and can never unlock, even with the right PIN.
- **D19. The PIN belongs to the profile**, set by that person, never visible to anyone; an administrator can reset it but never read it. NSFW mode (D23) locks again after 15 minutes idle (setting), on switching profile, and when the app closes. Entering a wrong PIN five times pauses unlocking for a few minutes.
- **D20. Where Vault shows up once unlocked:** one separate "Vault" area at the end of Watch (and nowhere else), viewed as D24 describes. A locked profile sees nothing at all, not even a locked door. Vault is Dashboard only in v1: no native apps, no TV apps, no casting, no offline downloads.
- **D21. One adult metadata plugin ships: Stash-box** (Shy, 2026-10-20, replacing "none bundled"). The Library supplies the hooks: a provider can declare itself adult-only; adult-only providers are asked only about Vault items, and non-adult providers (YouTube included) are never asked about them. The bundled Official plugin speaks the open stash-box standard, defaults to StashDB, and lets an administrator add other stash-box compatible servers by address and set the order they are tried in (ThePornDB can be added this way if it offers a stash-box compatible address, which the terms check confirms). It needs the person's own account key (kept in the secrets store), is bundled and pre-approved like the YouTube plugin (D7a) but stays inactive until a Vault library exists and the profile has NSFW access (D18, D25). Matching by a fingerprint of the file is a separate permission shown in plain words ("sends a fingerprint of your file") and is off until the administrator turns it on. Before it is built, Claude Code checks StashDB's and stash-box's terms for bundling and reports; if bundling is not allowed, the plugin ships as the first community plugin instead and Shy is told. Reason: Privacy, Extensibility and Maintenance.
- **D22. Richer browsing comes later; performers and studios are Vault-area views now (D28, D39).** Grouping Vault in more ways than the views of D39 and the viewing options of D24 waits for a follow-up once the access rules are proven. Stash (AGPL-3.0, so its ideas and public formats are reusable; its code is not copied here) is the reference for that follow-up.
- **D23. NSFW mode: a profile setting, not a hidden gesture** (Shy, 2026-10-20, replacing the earlier hidden-entry idea). (a) **Where it lives:** Settings > Profiles > the person's page has an "NSFW mode" switch. Turning it on makes the Vault area visible for that profile; turning it off hides everything again. (b) **Quick toggle (optional):** on the same page the person can switch on "Show an SFW/NSFW check in the top menu", which adds a simple SFW/NSFW check to the top-nav profile dropdown for easy switching. It is off until the person enables it. (c) **Temporary:** NSFW mode switches itself off after the idle time, on profile switch and when the app closes (settings; the idle time can be "never" for an Allowed profile). (d) **Only where it can apply:** a profile that is Off (every Kids and limited profile, and any adult an administrator hasn't opened it for) gets none of this: no switch, no dropdown check, no word about NSFW or Vault on its profile page or anywhere else. It is not drawn, rather than disabled. (e) **PIN:** when the profile's access mode is "PIN to unlock", turning NSFW mode on from either place asks for the PIN first; Allowed profiles need none. The PIN is set on the same profile page (own profile only), and an administrator can reset it but never read it. (f) **Locking is instant** from the top-nav check or by pressing Escape twice, which hides everything and returns to Home. Reason: Ease of use, and Privacy by not drawing anything for profiles that cannot use it.
- **D24. Ways to view Vault** (Shy asked for more options, 2026-10-20), each remembered per profile: **Layout:** Shelf rows (like Watch), Grid of covers, Details list, or Timeline by date added (like View photos). **Group by:** series/folder, tag, or date added. **Sort:** recently added, title, year, recently played. **Covers:** Show, Blur until pointed at, or Hide (plain initials), set by the person, and Blur is the suggested default. A **Blur toggle sits at the top of the Vault area and of its search results**, so covers can be unblurred or re-blurred in one tap without opening settings; the toggle is remembered per profile and every Vault view starts Blurred after the area locks and unlocks again. **Titles:** shown or hidden until pointed at. Saved views (a named layout, group and filter) are allowed. Performers and studios as ways to group come with D22.
- **D25. An administrator PIN is required before any Vault library exists** (Shy, 2026-10-20, as a safety feature). Today a profile PIN is optional (4 to 12 digits, with lockout, used to switch to a profile). Creating a Vault library, marking a folder Vault, or opening a profile's NSFW access requires the acting administrator's own profile PIN to be set first, and asks for it at that moment. The NSFW mode PIN (D19, D23) is a different PIN: a person's profile PIN never turns on NSFW mode and the NSFW PIN never signs in to the profile, and the Engine refuses to save the same digits for both. Removing the administrator PIN while a Vault library exists is refused with a plain message. Reason: Reliability and Privacy; prevent, don't patch.
- **D26. The folder you choose decides which lookup source applies; nothing is guessed from the files** (Shy asked 2026-10-20). Each Videos library has a "Look up details from" setting, set when the folder is added: a normal Videos library offers **YouTube** (on by default, used only for files where a YouTube ID is found, D7) or **None**; a Vault library offers **a Stash-box server** (the administrator picks the server and enters their own key; until then the library uses **None**) or **None**. A normal library can never use the Stash-box plugin and a Vault library can never use YouTube or any other non-adult source (D21). The setting can be changed later on the library's page, and a series can opt out. Local sources (file names, `.info.json`, `.nfo`) always apply regardless.
- **D27. Vault content stays out of every shared surface; Search inside NSFW mode is separate** (Shy, 2026-10-20). Outside NSFW mode, Vault items, their artwork, titles, tags, performers and studios appear nowhere: not on Home, not on People pages (D28), not in Search or its suggestions, not in genre or tag lists and filters, not in Series, Universes or Recently Added. Tags and studios from a Vault lookup are kept in the Vault area's own records and never create or join entries in the shared Tags or Series. Performers follow D28: they exist only inside the Vault area and are never added to the shared People pages. Inside NSFW mode, the Search box gets a separate "Vault" results group (never mixed into normal results) that searches only what is actually stored for those items: the file-derived title, description, tags and names, and whatever a lookup brought back. Artwork follows the person's cover mode (D24), including the Blur toggle at the top of the area and of its search results and is stored apart from normal artwork and served only to profiles with access. A video with no lookup has only its file-derived title to search by; the more is downloaded and stored, the more is searchable. Reason: Privacy and Uniformity.
- **D28. Performers live only inside the Vault area; People pages stay canonical-only** (Shy, 2026-10-20, replacing the earlier two-faced page idea). The shared People pages show only canonical people from normal sources, exactly as today, and never anything from a Vault lookup. Performers from a stash-box are records of the Vault area itself: a tiled "Performers" view (D39) where opening a tile shows the scenes of that performer that the person owns. Performers are never linked or merged with canonical people, so a performer who is also in a normal film simply has no connection between the two, and nothing adult can surface on a normal page. A performer record exists only while at least one owned scene refers to it. Reason: Privacy and Maintenance; prevent, don't patch.
- **D29. The Stash-box server needs an account key** (Shy asked 2026-10-20; to be confirmed in the terms check). As far as we know, StashDB and other stash-box servers require an account and an API key sent with every request, so the lookup cannot work without one. An administrator enters the server address and the key once on the plugin (not per profile); it is kept in the secrets store, shown only as "connected", never displayed again, and a Test button checks it. Without a key the library simply uses None (D26).
- **D30. Data pulled from a stash-box is checked before it is saved.** A result is accepted only when it is a strong match (a file fingerprint match, or a title that agrees with the video's length and date); weaker matches are not applied: the video stays Unmatched (D32). Every field is checked: sensible length and date range, markup and links stripped, language noted. The person's own edits always win. For each field Tuvima records its source: which server, when, and how it was matched.
- **D31. Artwork pulled from a stash-box is checked before it is used.** It is accepted only from the configured server's own image address (an allow-list, never an address inside a result), downloaded and stored locally (never shown from the remote site), and must open as a real image of an allowed type with a sensible size and shape for its use (cover or thumbnail). Embedded camera/location data is removed, duplicates are dropped, and a failed or unsuitable image leaves the generated still frame in place. Artwork is stored apart from normal artwork and served only to profiles with access.
- **D32. No review list: doubtful items simply stay Unmatched** (Shy, 2026-10-20). Uncertain or conflicting matches are never applied and never queued anywhere. The video shows in the Unmatched section (D40) and the person can open its detail page and press **Identify** for a manual lookup (D38). Nothing about Vault enters the normal Needs Review, its banner, count or notifications, or the live ingestion page. Vault ingestion progress appears only as a quiet "Vault activity" list inside NSFW mode. Reason: Ease of use and Privacy.
- **D33. Vault viewing leaves no trace outside NSFW mode.** Watching Vault items does not feed Continue Watching, recommendations, taste summaries, "previously on", Local AI plugins, webhooks, "who's watching" views for administrators, Now playing, or sharing links (Vault items cannot be shared). The page title, browser tab, history entries and the phone or computer's media controls and lock screen show a generic title (such as "Video"), never the real one. The idle timer for locking never interrupts a video that is playing.
- **D34. Adults-only confirmation and honesty about disk files.** Creating a Vault library asks the administrator to confirm that everyone who can unlock it is an adult and that the content is lawful. The screen says plainly that the files themselves are visible on disk to anyone who can browse that folder, and that backups include Vault data under the same rules. The recycle bin entries for Vault items are visible only inside NSFW mode.
- **D35. File fingerprints are computed on the machine, sent only with permission.** A simple file hash is computed first; a perceptual video fingerprint (the kind Stash uses) is a later addition and needs a licence check before any code is written. Nothing is sent without the separate fingerprint permission (D21).
- **D36. NSFW mode belongs to the device session, not the whole profile.** Switching it on a phone does not switch it on the television or another browser, and each session locks by itself (D23).
- **D37. How a file is matched to a stash-box record, strongest first** (Shy asked 2026-10-20; details to be confirmed against the server's published interface in the terms check). (1) **Fingerprints:** the Library computes fingerprints of the file on the machine and asks the server whether it knows them. Stash-box records carry three kinds: a short hash of the file's first and last blocks (OSHASH) and a full-file hash (MD5), which both identify an exact copy of the file, and a perceptual hash (PHASH), which recognises the same video even after it was re-encoded or resized. An exact fingerprint match is a strong match; a perceptual match is strong only when it is very close, and the duration must also agree. (2) **Product code:** many releases, especially Japanese ones, carry a studio product code in the file or folder name (for example ABC-123). The Library reads such a code from the name and looks for it in the record's code field; a match is strong only if the duration (and date, when known) also agree. (3) **Title and duration/date:** a match by name alone is weak and is not applied; the video stays Unmatched (D32). The Library only reads from the server; it never uploads or submits fingerprints. Every accepted match stores which of these signals decided it, and a disagreement between signals (for example a code that matches one record while the fingerprint matches another) is not applied and the video stays Unmatched.
- **D38. Reading names, and fixing a match by hand, borrow from Stash and Whisparr** (Shy asked 2026-10-20; public documentation read, see Gaps and drift). (a) **Filename patterns are settings, not code:** a Vault library has a list of name patterns made of parts (studio, date, title, performer, product code), a list of ignored words (release tags such as DVDRip or group names), and characters treated as spaces (default dot and underscore), the same idea as Stash's filename parser. They feed the matching of D37. (b) **Identify on the detail page:** an Unmatched video's page has an **Identify** button that searches the server (by the title the person types, the name pattern results, or the product code) and lists candidates. Picking one shows the current values beside the proposed ones with a tick per field, so the person accepts only the fields they want (Stash's review table). (c) **"None of these"** leaves the video Unmatched. (d) **Out of scope from Whisparr:** it finds and downloads releases through indexers, torrent and Usenet clients; Tuvima never downloads. Its one-copy-per-title rule, quality upgrades and release searching are not adopted.
- **D39. How the Vault area is organised** (Shy, 2026-10-20). Top of the area: the Blur toggle (D24), Search (D27) and the layout controls. The **main page of the area shows videos and images**, never performers or studios:  **Recently added** (the default; matched and unmatched together, newest first, with filter chips All / Matched / Unmatched and Videos / Images), **Scenes** (everything, sortable), **Folders** (series and sections from the folder layout, as for Videos) and **Unmatched** (a plain sortable list). **Images** (galleries from folders, with a viewer) is its own list too, and **Performers**, **Studios** and **Tags** are their own lists, reached from the Vault menu and never mixed into the main page; Performers and Studios are tiled lists. A matched video can appear under its performers, studio and tags; an unmatched video has none, so it appears only in Recently added, Scenes, Folders and Unmatched. Only what the person owns is listed: a performer or studio appears only if at least one of their scenes is in the library, and the library never shows scenes the person does not have. Opening a performer or studio tile shows the scenes of that performer or studio that the person owns (D28). Sorting: date added, title, release date (matched), duration, last played, name and scene count (performers and studios). **The layouts of D24 (Shelf rows, Grid, Details list and Timeline by date added) are available in every view**, so Recently added, Scenes, Folders and the others can each be shown as a timeline.
- **D40. Unmatched videos in the list** (Shy, 2026-10-20): an unmatched video is shown with a still frame from the video, a file-derived title and a small "Unmatched" mark. The Unmatched view is a plain sortable list (title, file name, length, size, date added) where each row opens the video's detail page and its **Identify** button (D38), plus an edit action for the title. Nothing is hidden or queued just for being unmatched.
- **D41. Artwork: what each card shows and how big it is** (Shy, 2026-10-20; stash-box image sizes to be confirmed against the server's interface). Cards: **Scene** cards are landscape 16:9; **performer** cards are portrait 2:3; **studio** cards are logos on a neutral tile; **tag** chips have no image. For a matched scene the card uses the stash-box scene image, else a chosen still frame; for an unmatched scene it uses one still frame picked at random once from the good frames of the video (never black, D11/WP7), then saved so it does not change on every visit. Performers use the best portrait stash-box image, cropped from the top-centre, and show initials if there is none. Studios use the stash-box logo, shown whole (not cropped). The library keeps the original capped at 2560 pixels on the long edge and makes web-sized copies for cards (scene 640 and 1280 wide, performer 400 and 800 wide, studio 300 wide), checked and stored as D31 says. Blur (D24) applies to every card image. **Optional extra, Vault only and off by default:** pointing at a matched scene card cycles through up to four local stills; this is separate from the normal Videos rule that declined hover previews.
- **D42. Identify and Change thumbnail are in the "..." menu of every video, everywhere** (Shy, 2026-10-20). Wherever a video or series appears (Watch shelves, series and standalone pages, search results, Recently added, and every Vault view) its "..." menu offers **Identify** and **Change thumbnail**, for people allowed to edit and on desktop only (editing is desktop-only, D13). **Identify** queues a lookup (D38) and appears only for a video that is not matched and not already waiting to be matched. Once pressed, or while the automatic lookup of ingestion is still queued or running, the same entry reads **Identifying…** (greyed out) until the lookup finishes. When it finishes with one strong match it is applied; with several candidates the page shows "Choose a match" with the side-by-side preview and tick per field; with none the entry returns as Identify with a note "No match found". A video that is already matched has no Identify entry; changing its match is done in edit mode through Match and Identity. The lookup: in a normal Videos library it looks up a YouTube video by a pasted link or ID (or clears a wrong match); in a Vault library it searches the stash-box server. **Change thumbnail** shows the candidate stills from the video (the good frames, D41), the matched image when there is one, and an upload option; a **Pick another** button chooses a different random still in one tap. The choice is saved and survives re-scans. Both are shortcuts into the edit mode that the Details overlay and edit mode spec defines: **Identify** opens the video's page in edit mode with the Match and Identity section open, and **Change thumbnail** opens it with Manage Artwork open (a thumbnail is a kind of artwork). The thumbnail candidates are shown inside Manage Artwork. In the "..." menu they sit after "Edit this video" and before Delete, which stays last and red, so that spec's menu order is unchanged and nothing new is built beside it. The items are not drawn for profiles that cannot edit, and Vault items follow every Vault rule (D17, D27).
- **D43. Bookmarks: one feature for books, audiobooks and videos, built on how audiobook bookmarks work today** (Shy, 2026-10-20, amended in versions 26 to 28). A bookmark is a saved position in a video or audiobook. In the player, **Bookmarks** opens one panel with two tabs, **Add** and **Saved**. Add captures the position at the moment the panel opens (so the moment is not lost while typing), shows the chapter name when there is one, lets the person preview the captured spot, and takes a **short note** of up to 200 characters and an optional **longer description** (up to 4,000 characters). Saved lists that title's bookmarks, newest first, with jump-to and delete. **Quick look:** when a bookmark's tick on the progress rail is pointed at (hover on desktop, a tap on touch), a small card shows the short note; if a longer description exists, the card has a "More" link that opens it. The Saved list shows the short note and expands to the longer one. **Two kinds:** *personal* bookmarks belong to the profile that made them; *global* bookmarks exist for everybody who can see the title. Only server administrators can make, edit or delete global bookmarks (Add shows a "Share with everyone" switch only to them; the switch is off by default, so every new bookmark is personal and sharing is a deliberate choice each time; and the Engine checks the permission, not the Dashboard), and a global bookmark looks different (another tick shade and a small "Everyone" label) so people know whose it is. Everyone sees global bookmarks on titles they can see, and cannot change them. Ticks show on the progress rail beside the file's own chapters, which stay read-only. A bookmark can optionally have an **end time**, which makes it a part of the video (a scene): the rail shows it as a shaded span and the Saved list offers **Play this part**, which plays from the start and stops at the end. There are no tags in v1. Adding a bookmark is a personal action, not catalogue editing, so it works on tablet and phone and does not need edit mode. In the Vault, bookmarks (global ones too) follow every Vault rule (D17, D27, D33): invisible outside NSFW mode, their notes and descriptions searchable inside it, and absent from history, AI and webhooks.
- **D43a. One word everywhere: Bookmarks** (Shy, 2026-10-20, after weighing Markers). Books, audiobooks and videos all call a saved spot a Bookmark; nothing is renamed in audiobooks or the book reader, and the earlier idea of renaming audiobook bookmarks to Markers is dropped. Audiobooks gain the same short note, longer description, optional range and shared bookmarks as videos; existing audiobook bookmarks stay personal, with their text as the short note. Stored data, internal names and wire names are unchanged. The bookmark icon already exists and is reserved for real bookmarks.
- **D46. Bookmarks can be exported and imported as a bookmark pack** (Shy, 2026-10-20). From a title's Saved list a person chooses **Export**, picks which of their bookmarks to include, reviews them, and saves a small pack file. A pack contains only: how to recognise the title (its canonical IDs such as IMDb/TMDB, or a YouTube ID, plus its running time and edition), and for each bookmark its time, optional end time, chapter name, short note and longer description. It never contains file paths, profile names or what anyone watched. **Import** reads a pack, checks it is for this title, and adds its bookmarks as **pack bookmarks**: a third kind, read-only, labelled with the pack's name and author, shown with their own tick shade, and switchable off per pack. If the pack is for a different cut (for example Theatrical against Extended) the import says so and offers to align by chapter or to skip. Bookmarks from the Vault are never exportable. Pack bookmarks follow all other bookmark rules.
- **D47. Placeholder: the "Popular Bookmarks" plugin** (Shy, 2026-10-20; not built in this spec). A plugin would offer ready-made bookmark packs for well-known titles (for example the Battle of Gondor in a film) so a person sees those parts as selections in their own copy without marking anything up. It would read packs from the community plugin repository when that exists, and install them through the plugin approval rules. Built on D46's pack format and the plugin platform of the Developer tools spec. Reserved here so the pack format is designed to carry it.
- **D48. Community sharing and review is a separate plan** (Shy, 2026-10-20). How people submit, review, trust, update and remove shared things such as bookmark packs, and how the community plugin repository handles them, is its own planning job covering more than bookmarks (plugins, packs, other shared items). This spec only fixes the pack format and local import/export.
- **D44. Images are part of the same area and reuse View's gallery system** (Shy, 2026-10-20). The Vault holds videos and images together. Its image side is built on what View already does for photos: the scanner and thumbnails, galleries (hand-made and smart-rule galleries), the timeline, the viewer and tags, so a person gets the same gallery behaviour they already know, with the Vault's rules on top: separate storage and artwork, access and NSFW mode (D17, D23), isolation from search, Home, history and AI (D27, D33), Blur on every thumbnail (D24) and the recycle-bin rule (D14). There is no outside lookup for images in v1. Matching images to performers or scenes is a later extension.
- **D45. A fourth top-level area, hidden until NSFW mode** (Shy, 2026-10-20). Beside Read, Listen, Watch and View there is one more area for adult material (named the Vault, Shy 2026-10-20, R19). It holds both videos and images. It does not appear anywhere (menu, Settings, Libraries list, Add folder, search) until NSFW mode is on for that device session (D23, D36), and a profile that is Off never sees it (D18). Its library settings live inside the area itself, not in the normal Libraries list. It is separate from the Videos type: the Videos type (WP1) stays the normal, non-adult Watch shelf, and nothing in Videos is marked or hidden. Adding a folder to it is a separate third choice that exists only in NSFW mode (D3, WP2). Isolation (D27, D33) is the same as before, but now also structural: items live in the area, not as flagged items among normal ones. Reason: Privacy and Ease of use; prevent, don't patch.

## 5. Data / model changes

- **A new media type, Video.** It is a catalogue type that uses local identity only: no movie, TV or book providers are called for it. Works, a Series (Collection) and files (Media Assets) are created as for TV, with an identification record saying how each was identified. Resume and Up Next use the same per-profile progress records as every other title (progress is stored against the video's file record).
- **Stable identity:** a video keeps its progress when it is renamed or moved inside the folder (identity comes from relative path plus file content fingerprint).
- **Custom order** stored in a small order table; per-series settings (lookup on/off).
- **Config:** title-cleaning rules (leading numbers, separators, resolution tags, `[youtubeid]` suffixes) and the identification order live in `config/`, not code; the YouTube provider is a file in `config/providers/`; any key in `config/secrets/`.
- **What the code check found (2026-10-20):** six library types are written into the Libraries panel and its checks; today the checks forbid a Watch library from skipping outside lookups (so the original "just add a config entry" idea doesn't work, and a validator change is part of WP1); View videos are plain files with no resume; nothing named Videos exists, so no clash. Pre-release: a data store reset and re-ingest is acceptable.

## Plain English summary

Videos gets its own shelf in Watch for downloads, courses and saved YouTube channels. A folder becomes a series, sub-folders become sections and files become episodes, and Tuvima remembers where you stopped. YouTube downloads are recognised from their file names and a small lookup fills in titles and thumbnails. Phone memories stay with your photos, and when you add a folder Tuvima asks which kind it is and nudges you if it looks like phone footage. Deleted videos go to a recycle bin, kids' profiles do not see Videos unless an administrator allows it, and videos get the same Bookmarks as audiobooks, which are renamed from Bookmarks.

Separately, a new top-level area called the Vault holds adult videos and images. It does not exist on screen until a person with access turns on NSFW mode, which needs their own PIN, and an administrator PIN must be set before any Vault can be created. Vault content never shows in Home, search, People pages, history or notifications outside NSFW mode, uses the same gallery tools as View, and is looked up through a bundled Stash-box plugin that identifies files by fingerprint or product code and leaves doubtful ones Unmatched for you to Identify by hand. It is built in three waves after the current ingestion and Developer tools work.
